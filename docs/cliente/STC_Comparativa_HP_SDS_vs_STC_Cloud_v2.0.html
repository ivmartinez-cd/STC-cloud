1. Introducción y Contexto del Análisis

HP Smart Device Services (SDS) es la plataforma de gestión remota de impresoras de HP, compuesta por el HP SDS Manager Data Collection Application (DCA) que se instala on-site —conocido internamente como JAMC— y la infraestructura cloud HP SDS Cloud, operada bajo los estándares ISO 27001 / SOC2 por EKM Global.

STC Cloud Monitor es una plataforma propia de monitoreo multi-marca, construida sobre principios similares (agente local → cloud → API) pero con prioridades distintas: soporte nativo de múltiples fabricantes (HP, Samsung, Lexmark, Ricoh, Brother, Epson, Canon, Konica Minolta, Xerox), despliegue sin dependencia de infraestructura HP, y menor fricción de instalación para redes corporativas medianas.

El análisis se apoya en los documentos técnicos oficiales HP SDS disponibles: Monitoring Loops White Paper (Jan 2020), Security White Paper, DCA IMIL Commands v29, System Requirements v2.6, Installation Guide v1.2 y Secure by Default Initiative White Paper.

2. Arquitectura de Comunicación: XMPP vs WebSocket

Decisión intencional
HP SDS / JAMC
  • Canal de control: XMPP (puerto TCP 5222, salida)
  • Canal de datos: HTTPS (puerto 443, salida)
  • JAMC sólo genera conexiones salientes (Zero-Inbound)
  • Requiere apertura explícita de puerto 5222 en firewall
  • XMPP habilita mensajería push en tiempo real desde HP Cloud hacia el agente
STC Cloud Monitor
  • Un único canal: WebSocket Seguro (WSS) sobre HTTPS puerto 443
  • Agente sólo genera conexiones salientes (Zero-Inbound equivalente)
  • No requiere abrir puertos adicionales al 443 estándar
  • Bi-direccional: el servidor puede enviar comandos via WebSocket

Justificación de la decisión

El puerto 5222 (XMPP) está bloqueado en la mayoría de firewalls corporativos por defecto. Forzar su apertura genera fricción de instalación y requiere coordinación con el departamento de IT del cliente. Al unificar todo el tráfico sobre WSS/443, STC Cloud simplifica drásticamente el despliegue: el mismo puerto que usa el navegador web funciona para el agente sin necesidad de cambios en la política de red.

La contrapartida es que WebSocket no es un protocolo de mensajería estándar con presencia nativa en el ecosistema de telecomunicaciones; XMPP es robusto y tiene mecanismos de store-and-forward más maduros. Esta diferencia es aceptable dado el perfil de cliente objetivo.

3. Descubrimiento de Dispositivos

Decisión intencional
HP SDS / JAMC
  • Ping ICMP para verificar alcanzabilidad
  • SNMP broadcast/walk sobre rangos IP
  • SLP (Service Location Protocol) UDP 427 — descubrimiento automático local
  • WS-Discovery UDP 3702 — descubrimiento de dispositivos modernos
  • Los 4 métodos trabajan en paralelo para máxima cobertura
STC Cloud Monitor
  • TCP connect a puertos de impresora: 9100 (RAW), 631 (IPP), 80 (HTTP/EWS), 443 (HTTPS/EWS)
  • Scan sobre rangos IP configurados por el administrador
  • Sin ICMP, sin UDP, sin broadcast
  • Timeout diferenciado: 500ms puertos de impresora, 2000ms puertos web

Justificación de la decisión

El enfoque de STC Cloud de escanear puertos TCP tiene tres ventajas clave respecto al modelo HP:

  • Sin dependencia de ICMP: Muchas redes corporativas bloquean ping por política. Un escaneo TCP funciona igualmente aunque ICMP esté desactivado.
  • Sin UDP: SLP (UDP 427) y WS-Discovery (UDP 3702) suelen estar bloqueados en switches gestionados y VLANs segmentadas. TCP connect siempre funciona si el dispositivo está accesible.
  • Multi-marca desde el primer momento: SLP y WS-Discovery tienen mayor adopción en dispositivos HP. Los rangos TCP son agnósticos al fabricante: cualquier impresora que tenga un puerto de servicio abierto es descubierta independientemente de la marca.

La contrapartida es que el escaneo TCP es más lento que un broadcast UDP y puede generar más tráfico de red visible en logs de firewall. Para los volúmenes típicos de instalación de STC Cloud (200–500 impresoras por sitio) este coste es despreciable.

HP SDS Discovery:
  ICMP ping sweep → SNMP walk → SLP multicast (UDP 427) → WS-Discovery (UDP 3702)
  ↓ Muchos vectores, pero varios bloqueados en redes corporativas segmentadas

STC Cloud Discovery:
  TCP connect a puertos [9100, 631, 80, 443] sobre rangos IP configurados
  ↓ Un único vector, siempre funcional si hay conectividad IP básica
     Timeout 2000ms en 80/443 para firmware lento (Samsung SyncThru antiguo)
Nota sobre WS-Discovery. WS-Discovery (UDP 3702) es utilizado por HP en modelos con FutureSmart 4.x. Su adopción fuera del ecosistema HP es limitada. Añadir soporte WS-Discovery en STC Cloud tendría valor marginal dado que la base instalada multi-marca prioriza los puertos TCP estándar.

4. Bucles de Monitoreo y Frecuencias

Parcialmente implementado   Mejora pendiente

HP SDS: 5 bucles especializados

HP SDS organiza la recolección en cinco bucles independientes con frecuencias diferenciadas según horario laboral (08:00–18:00 L-V) y fuera de horario:

Bucle Datos recogidos En horario laboral Fuera de horario
Identity Modelo, serial, firmware, IP, MAC Cada 10 min Cada 60 min
Alert Alertas de estado (papel, error, atasco) Cada 3 min Cada 15 min
Meter Contadores de páginas (mono/color/total) Cada 20 min Cada 240 min (4h)
Consumables Niveles de tóner, cartuchos, drum Cada 60 min Cada 240 min (4h)
Tray/Media Estado de bandejas, tipo de papel Cada 480 min (8h) Cada 480 min (8h)

Los bucles de Alert y Meter acumulan datos localmente y los envían a HP SDS Cloud en lotes: Alert en tiempo real, Meter una vez por día. Esto reduce el tráfico de red manteniendo resolución alta para las alertas que importan operativamente.

STC Cloud: Tres bucles especializados con conciencia horaria

STC Cloud ejecuta tres bucles independientes con conciencia de horario laboral (L-V 08:00–18:00, zona horaria Argentina), alineados directamente con las frecuencias de HP SDS:

Bucle STC Equivalente HP SDS Datos recogidos En horario laboral Fuera de horario Fuente primaria
Discovery Identity Descubrimiento de dispositivos nuevos, marca, modelo, serial Cada 10 min Cada 60 min SNMP
Meter Meter Contadores de páginas (mono/color/total) Cada 20 min Cada 4h EWS → SNMP fallback
Supplies Consumables Niveles de tóner + código, serial y capacidad de cartucho Cada 60 min Cada 4h EWS únicamente

Los tres bucles se autoprograman al finalizar cada ciclo, recalculando el intervalo en función del horario en ese momento exacto. El bucle de descubrimiento arranca inmediatamente al inicio del agente; meter y supplies arrancan 2 minutos después para que el descubrimiento inicial pueble la base de datos de dispositivos conocidos.

Diferenciador EWS-first

A diferencia de HP SDS, que usa SNMP como protocolo central incluso para contadores, STC Cloud prioriza EWS (HTTP/HTTPS directo a la impresora) como fuente de datos para ambos bucles. SNMP se utiliza únicamente como fallback en dispositivos que no exponen EWS. Esta filosofía permite recolectar datos ricos (código de cartucho, número de serie, capacidad, páginas impresas estimadas) que no están disponibles por SNMP estándar.

Gap residual

  • Sin datos de firmware: El bucle Discovery captura marca, modelo y serial, pero no la versión de firmware del dispositivo, a diferencia del Identity loop de HP SDS.
Decisión de diseño. Los bucles de alertas operativas (papel, atasco) y de bandejas/papel están deliberadamente fuera del scope de STC Cloud Monitor. El foco de la plataforma es la recolección de contadores y consumibles para gestión de flota, no la monitorización operativa en tiempo real. Para atascos y bandejas, el usuario final actúa directamente sobre la impresora.

5. Soporte de Protocolo SNMP

Resuelto (agosto 2026)
HP SDS / JAMC
  • SNMPv1, v2c, v3
  • Auth: MD5, SHA-1, SHA-224, SHA-256, SHA-384, SHA-512
  • Privacidad: AES-128, AES-192, AES-256, DES
  • Comunidades v1/v2c configurables por grupo de dispositivos
  • Credenciales gestionadas por CLI (snmpset, snmpadd)
STC Cloud Monitor
  • SNMPv1, v2c, y v3 (MD5/SHA-2, DES/AES)
  • Lista de hasta 8 credenciales por agente, probadas en orden hasta que una responda (fail-fast si el host no da señal de vida)
  • Credenciales cifradas at-rest (AES-256-GCM, clave derivada con HKDF-SHA256) — nunca en claro en DB ni logs
  • Credenciales por rango de IP: un rango puede restringirse a un subconjunto de la lista (útil si distintas VLANs de impresoras usan comunidades distintas)
  • Reorder/renombrar/borrar sin re-tipear secretos (referencia opaca por id); optimistic locking contra ediciones concurrentes en el portal

SNMPv3 provee autenticación de mensajes (HMAC) y cifrado de payload — cierra la brecha que existía en v1.0, donde SNMPv2c en redes con política estricta era inaceptable (comunidades en claro). Probado contra un agente SNMPv3 real simulado con net-snmp, no sólo con sesiones mockeadas.

Lo que no se hizo: rotación de la clave de cifrado en sí (el ciphertext ya lleva un prefijo de versión para no bloquearla a futuro, pero el mecanismo de rotación no está implementado).

6. Identidad Persistente del Dispositivo

Resuelto (agosto 2026)
HP SDS / JAMC
  • Identidad primaria: MAC address + Serial Number
  • El device ID persiste aunque la impresora cambie de IP
  • MAC se obtiene vía SNMP (ifPhysAddress)
  • Correlación automática si la impresora es movida a otra subred
STC Cloud Monitor
  • Identidad primaria: (client_id, Serial Number) — clave compuesta, no sólo el serial
  • MAC address capturada y almacenada como campo secundario
  • Decommission (soft-delete + reactivar) en vez de borrado directo
  • Mover un equipo entre agentes/clientes con confirmación explícita si cambia de cliente
  • Merge manual de duplicados ya creados: historial de lecturas sumado, el registro fuente queda como lápida (merged_into) en vez de desaparecer

La clave compuesta (client_id, serial) — en vez de (agent_id, serial) como antes — resuelve el caso que v1.0 no cubría: dos agentes del mismo cliente viendo la misma impresora (ej. tras reinstalar el agente) ya no la duplican. Para los duplicados que ya existían antes de este cambio, se agregó una herramienta de fusión manual desde el portal en vez de intentar una migración automática (que podría fusionar equipos que en realidad son distintos).

Lo que no se hizo: corrección 100% automática de duplicados por reasignación de IP — sigue habiendo una ventana de staleness entre que DHCP reasigna una IP y el próximo scan corrige la identidad (mitigada, no eliminada; ver también la nota de staleness del acceso remoto EWS en §7).

7. Acceso EWS Remoto vía Nube

Resuelto (agosto 2026)

HP SDS provee una funcionalidad llamada Remote EWS: el administrador puede acceder a la interfaz web integrada (EWS) de cualquier impresora HP a través de un túnel cifrado establecido desde HP SDS Cloud hacia el JAMC local, sin necesidad de VPN ni de IP pública en la impresora. Esta funcionalidad está desactivada por defecto y requiere whitelisting explícito del cliente.

STC Cloud implementa un mecanismo equivalente reusando el canal WSS ya existente (el mismo que hoy manda comandos remotos): el cloud le pide al agente un único GET a una ruta de la EWS de un dispositivo específico, el agente lo ejecuta dentro de la LAN del cliente y devuelve el resultado por el mismo canal — sin sesión de túnel persistente, cada llamada es un request/response independiente.

HP SDS / JAMC
  • Desactivado por defecto, whitelisting explícito del cliente
  • Túnel cifrado persistente vía XMPP/HTTPS
STC Cloud Monitor
  • Desactivado por defecto (agents.remote_ews_enabled), opt-in explícito por agente
  • Proxy de un solo GET por vez, sin sesión persistente, sobre el WSS ya existente
  • Allowlist en dos capas: el cloud sólo permite IPs de dispositivos ya sincronizados de ese agente (nunca una IP tipeada a mano); el agente vuelve a validar contra su catálogo local antes de conectar
  • Rechaza si el dispositivo no reportó recientemente (ventana de staleness — mitiga el riesgo de una IP reasignada por DHCP apuntando a otro equipo)
  • Sólo GET — nunca puede mutar configuración de la impresora, mismo principio que el resto del motor de captura
  • Tope de 2MB por respuesta, cortado en streaming; auditado (qué ruta se pidió, nunca el contenido) en cada llamada

Un detalle de diseño no trivial: la implementación tuvo que asegurarse de que el contenido de la EWS de un cliente sólo llegue a quien lo pidió, no a cualquier otro administrador con sesión abierta en el portal en simultáneo — el canal de difusión de resultados de comandos que ya existía enviaba a todos los portales conectados, y hubo que resolver este caso puntual por separado antes de exponerlo.

Lo que no se hizo: paridad completa con las funciones IMIL de HP SDS que acompañan a su Remote EWS (MIB walk remoto, deshabilitar monitoreo por equipo desde la consola, reenviar lecturas puntuales, descubrir una IP puntual desde el portal) — sólo se implementó el acceso a la EWS en sí. Tampoco hay todavía UI de portal para invocarlo (por ahora es un endpoint REST); y la activación del flag y su uso comparten el mismo nivel de permiso (admin/operator), sin un consentimiento explícito adicional del cliente como sugiere el modelo de whitelisting de HP.

8. HP Secure by Default y Riesgos en FutureSmart 4.5+

Riesgo técnico

HP introdujo en FutureSmart 4.5 (firmware de impresoras HP de gama empresarial, ~2020 en adelante) una política de seguridad activada por defecto que afecta directamente a los mecanismos que STC Cloud utiliza para la recolección de datos:

Funcionalidad afectada Comportamiento en FS4.5+ Impacto en STC Cloud
SNMP v1/v2c (escritura) Desactivado por defecto (sólo lectura) Bajo — STC Cloud sólo lee SNMP, no escribe
SNMP v1/v2c (lectura) Activo por defecto, comunidad public Ninguno actualmente — pero política enterprise puede desactivarlo
PJL Device Access Commands Desactivado por defecto Alto — si STC Cloud usa PJL para contadores, falla silenciosamente
PJL Drive Access Desactivado por defecto Medio — no usado actualmente pero bloquea futuros usos de PJL
TLS 1.0 / 1.1 Desactivado por defecto Bajo — fetchHttp usa Node.js con TLS 1.2+ por defecto
CSRF en EWS Activado por defecto en operaciones de configuración Ninguno — STC Cloud sólo hace GET de lectura, no modifica configuración
Account Lockout (EWS) Activo: 5 intentos fallidos → bloqueo 10 min Ninguno — STC Cloud no autentica en EWS (páginas públicas)
Acción recomendada. Auditar los OIDs y endpoints EWS utilizados para impresoras HP empresa y confirmar que ninguna ruta de código use PJL como fuente de contadores. Documentar esta dependencia ausente. Si en el futuro se implementa soporte PJL, añadir detección del flag FS4.5 antes de enviar comandos PJL.

9. Capacidades No Implementadas

9.1 Monitoreo de Bandejas y Papel

Fuera de scope

HP SDS recoge estado de bandejas (nivel de papel, tipo de papel configurado) vía su bucle Tray/Media cada 8 horas. STC Cloud no implementa ni planea implementar esta funcionalidad: el foco de la plataforma es la gestión de flota (contadores y consumibles), no la monitorización operativa del estado de la impresora. El usuario final actúa directamente sobre la impresora cuando detecta una bandeja vacía.

9.2 Actualización de Firmware Remota

Fuera de scope actual

HP SDS JAMC puede recibir instrucciones de HP Cloud para descargar y aplicar actualizaciones de firmware en dispositivos HP. STC Cloud no implementa ni planea implementar esta funcionalidad: el riesgo operativo de un firmware push automático sobre impresoras de producción sin intervención humana explícita supera los beneficios para el perfil de cliente objetivo. Se mantiene deliberadamente fuera de scope.

9.3 Alertas Operativas en Tiempo Cuasi-Real

Fuera de scope

El bucle Alert de HP SDS sondea el estado del dispositivo cada 3 minutos durante horario laboral para detectar atascos, bandeja vacía o errores de hardware. STC Cloud no implementa ni planea implementar un bucle de alertas operativas: la plataforma está orientada a la gestión de flota (contadores y consumibles), no a la monitorización del estado operativo en tiempo real. Esta distinción es intencional y alinea el producto con su propuesta de valor diferencial frente a HP SDS.

9.4 Instancias Múltiples del Agente por Sitio

A mejorar   Prioridad 3

HP JAMC permite desplegar múltiples instancias DCA en el mismo site para escanear subredes distintas o proporcionar alta disponibilidad. STC Cloud contempla un único agente por site. En clientes con múltiples VLANs de impresoras que no se rutan entre sí, el agente actual no puede cubrir todas las subredes desde un único punto de instalación.

10. Modelo de Datos y Retención

Resuelto (agosto 2026)
HP SDS
  • Retención cloud: 10 años
  • Histórico de contadores completo para análisis de tendencias
  • Datos anónimos mediante GUID de cliente (privacidad)
  • Datos accesibles vía ISV/MPS API con historial completo
STC Cloud Monitor
  • Retención local (SQLite): 7 días de backlog (sin cambios)
  • Retención cloud, ahora formal: readings crudo 24 meses (TimescaleDB, add_retention_policy nativo), agent_logs 90 días, alertas resueltas 12 meses (las abiertas nunca se purgan)
  • audit_logs deliberadamente sin purga automática — un trail de auditoría no debe autopurgarse solo
  • Agregados diario/mensual sin vencimiento — sobreviven a la purga del dato crudo, pensados para tendencias de largo plazo sin necesitar 24 meses de filas individuales

Las ventanas elegidas (24 meses de dato crudo, agregados indefinidos) son una decisión de negocio — no hay ningún requisito regulatorio específico que exija un número exacto para este tipo de dato operativo, a diferencia de lo que podría sugerir el ejemplo de "10 años" de HP SDS (que además aplica a un contexto de certificación ISO 27001/SOC2 distinto al de STC, ver §13). Los agregados continuos (TimescaleDB continuous aggregates, refresco automático cada 1-6h) acercan la propuesta de "tendencias de largo plazo" de HP sin necesitar retener el dato crudo indefinidamente.

Lo que no se hizo: anonimización explícita de datos de cliente (no aplica igual que en HP SDS — STC Cloud no recolecta PII de por sí, ver el inventario de datos, así que no hay dato de persona que anonimizar).

11. API Pública e Integración con Terceros (ISV/ERP)

Nuevo (agosto 2026)
HP SDS
  • API para MPS/ISV con historial completo de contadores
  • Integración pensada para partners de facturación grandes
STC Cloud Monitor
  • API keys por cliente (hash SHA-256 at-rest, se muestra en claro una sola vez al crearla)
  • Endpoints de lectura: dispositivos, lecturas, alertas, cierres de reporte — siempre acotados al cliente dueño de la key
  • Webhooks de integración (lecturas/alertas/cierres) firmados con HMAC-SHA256, para que el ERP del cliente verifique autenticidad
  • Reusa el mismo guard anti-SSRF ya construido para las notificaciones internas (HTTPS únicamente, rechaza IPs privadas/loopback/metadata)

A diferencia de HP SDS (pensado para partners grandes de MPS), la API pública de STC Cloud está orientada a que el propio cliente final conecte su ERP o sistema de facturación interno sin intervención de STC. Cada cliente gestiona sus propias keys y su propio webhook — STC no necesita mediar la integración.

Lo que no se hizo: UI de portal para gestionar keys/webhooks (por ahora sólo REST); expiración automática de keys (se revocan a mano, igual que un token de acceso personal de GitHub); documentación pública tipo OpenAPI/Swagger.

12. Resiliencia del Agente

Nuevo (agosto 2026)

Un conjunto de mejoras operativas al agente DCA, sin equivalente directo en la comparativa original pero relevantes para la robustez de un despliegue de largo plazo:

  • Rollback de actualización: antes, una actualización remota reemplazaba el binario in-place sin ningún respaldo — un release roto no tenía forma de revertirse salvo reinstalar a mano. Ahora se guarda una copia de la versión anterior antes de reemplazar, restaurable bajo demanda.
  • Activación resiliente a cortes de red: antes, si no había conectividad al momento de instalar, la activación fallaba una sola vez y el servicio quedaba detenido indefinidamente. Ahora reintenta con backoff creciente ante error de red (nunca ante una clave inválida, para no encadenar intentos inútiles).
  • Dedupe de lecturas idénticas: un equipo ocioso generaba una fila nueva en cada ciclo de meter/consumibles aunque nada hubiera cambiado. Ahora sólo se envía si cambió algo relevante o pasaron 4 horas desde el último envío (para no perder la señal de "sigo vivo").
  • Detección de PJL deshabilitado: HP FutureSmart 4.5+ desactiva PJL por defecto (ver §8) — ahora el agente detecta y loguea cuando un equipo deja de responder a PJL de forma consistente, en vez de fallar en silencio.
  • Rotación de logs real: antes un solo nivel de respaldo (se pisaba en cada corte). Ahora rota en cadena hasta 5 archivos, mismo criterio que logrotate.

La ausencia de certificaciones formales no es un bloqueante para el perfil de cliente objetivo de STC Cloud (empresas medianas en Argentina y Latinoamérica). Esta diferencia se documenta como conocida y conscientemente fuera de scope, no como una deuda técnica.

15. Hoja de Ruta de Mejoras Priorizadas

De los 6 puntos de mejora priorizados en v1.0 (mayo 2026), 5 ya están resueltos (marcados abajo). Quedan genuinamente pendientes 2 ítems — uno operativo, uno de certificación formal — más los que surgieron de esta misma pasada de trabajo (remote EWS con paridad IMIL completa, UI de portal para API pública, backend multi-réplica).

Auditoría de uso de PJL en HP FutureSmart 4.5+
Resuelto

El motor de captura ya usa EWS como fuente primaria de contadores, con PJL sólo como fallback — y desde agosto 2026 el agente además detecta y loguea cuando un equipo deja de responder a PJL de forma consistente (posible firewall/firmware con PJL deshabilitado), en vez de fallar en silencio.

Soporte SNMPv3
Resuelto

v1/v2c/v3 (MD5/SHA-2, DES/AES), lista de hasta 8 credenciales por agente o por rango de IP, cifradas at-rest. Ver §5.

Política formal de retención de datos cloud
Resuelto

Crudo 24 meses (TimescaleDB nativo), agregados diario/mensual sin vencimiento, agent_logs 90 días, alertas resueltas 12 meses. Ver §10.

Identidad de dispositivo con MAC address
Resuelto

MAC capturada como campo secundario, más una solución más completa de lo planteado originalmente: clave compuesta (client_id, serial) y herramienta de fusión manual de duplicados ya existentes. Ver §6.

Acceso EWS remoto vía nube
Resuelto (parcial)

Implementado el acceso a la EWS en sí (proxy de un GET, opt-in, allowlist en dos capas). Ver §7 para el detalle de lo que queda pendiente (paridad IMIL completa, UI de portal).

Múltiples agentes por site (multi-subred)
P3 Largo plazo

Sigue sin resolverse. Permitir registrar y gestionar más de un agente bajo el mismo site/cliente en la plataforma cloud. Imprescindible para clientes con redes segmentadas (múltiples VLANs de impresoras sin enrutamiento entre sí) o con oficinas remotas bajo el mismo contrato. Requiere cambios en el modelo de datos del servidor y en la interfaz de administración.

Backend multi-réplica
P3 Largo plazo

Sigue sin resolverse — decisión de arquitectura pendiente, no un descuido. El registro de sockets WS activos vive en memoria de un único proceso; escalar a múltiples réplicas del backend requeriría pub/sub Redis para el WS y decidir si vale la pena migrar los jobs periódicos (hoy setInterval simple, deliberadamente NO BullMQ repeatable — la Redis de producción usa una política de desalojo que podría perder el estado de un job repetible en silencio).

UI de portal para API pública y Remote EWS
P3 Largo plazo

Ambas funcionalidades (§7 y §11) son sólo REST por ahora — un administrador necesita curl/Postman hasta que exista una UI dedicada en el portal.

Ventajas diferenciales de STC Cloud que no tiene HP SDS. STC Cloud presenta ventajas estructurales propias que no son mejoras de HP sino diferenciadores: (1) soporte nativo de 9+ fabricantes frente al ecosistema exclusivamente HP de SDS; (2) sincronización al servidor cada 30 segundos frente a lotes diarios para contadores; (3) despliegue sin apertura de puertos adicionales (sólo 443); (4) agente sin dependencia de infraestructura HP Cloud, eliminando el riesgo de discontinuación del servicio por parte del fabricante; (5) agregados continuos de TimescaleDB para tendencias de largo plazo sin necesitar retener el dato crudo indefinidamente; (6) API pública orientada a que el cliente final integre su propio ERP, sin intermediación de STC.
