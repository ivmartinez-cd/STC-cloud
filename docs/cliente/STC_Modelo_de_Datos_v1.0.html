1. Alcance y Lectura del DER

1. Alcance, Cifras y Cómo Leer el DER

Este documento describe el esquema de la base de datos de STC Cloud: qué tablas existen, qué guarda cada una, cómo se relacionan y por qué están diseñadas así. Es la explicación que acompaña al DER (Diagrama Entidad-Relación) que genera cualquier cliente SQL, como DBeaver, sobre el schema public.

Todo lo que sigue fue verificado contra la base real el 12 de septiembre de 2026 leyendo directamente el catálogo de PostgreSQL (columnas, tipos, claves, índices, constraints, vistas y políticas de TimescaleDB). El esquema se construye exclusivamente con las 75 migraciones versionadas de Knex que viven en el repositorio y que la API aplica al arrancar; no hay cambios manuales en producción.

QuéCantidad
Tablas35 (33 de negocio + 2 internas de Knex)
Vistas3 (2 agregados continuos de TimescaleDB + 1 vista SQL)
Foreign keys declaradas63
Constraints CHECK44
Índices además de las claves primarias64 (varios parciales y por expresión)
Hypertables (TimescaleDB)1 (readings)
Triggers1 (agents_client_id_sync)

Cómo leer el diagrama que genera DBeaver

  • Cada caja es una tabla. La fila en negrita al tope es la clave primaria.
  • Los iconos a la izquierda de cada columna indican el tipo: A-Z texto, 123 número, reloj fecha/hora, { } JSON, tilde booleano.
  • Cada línea es una foreign key declarada en la base. Si dos tablas se relacionan sólo por convención del código, no hay línea (el caso concreto se explica en la sección 11).
  • Las cajas con icono de ojo no son tablas sino vistas: no ocupan espacio propio, se calculan a partir de otras.
Para reproducir el DER: en DBeaver, desplegar stc_cloud → Schemas → public, clic derecho sobre public y elegir View Diagram. El layout automático apila todo en una columna; conviene arrastrar clients y users a los costados y devices al centro, y guardar el diagrama para no rehacerlo. Se exporta a PNG o SVG desde el menú contextual.

2. Vista General

2. Vista General del Modelo

El modelo tiene dos "hubs" hacia los que convergen casi todas las líneas del diagrama. clients es el tenant: casi toda tabla de negocio lleva client_id, la columna por la que se aísla la información entre clientes. users recibe todas las foreign keys de auditoría de acciones humanas: created_by, closed_by, assigned_to, resolved_by, updated_by.

La cadena operativa principal es cliente → agente → dispositivo → lectura. De los dispositivos cuelgan las alertas, los incidentes, los pedidos de insumos y las líneas de los cierres de facturación.

Composición (ON DELETE CASCADE)

Lo que no tiene sentido sin su padre desaparece con él: lecturas de un equipo, eventos de un incidente, equipos de un agente, todo lo que cuelga de un cliente.

Referencia (ON DELETE SET NULL)

Los vínculos de auditoría y los opcionales sobreviven al borrado del referido: un incidente conserva su historia aunque se borre el usuario o el equipo.

3. Convenciones Transversales

3. Convenciones Transversales

Estas reglas se repiten en todo el esquema y explican la mayor parte de lo que se ve en el DER. Conocerlas evita leer tabla por tabla.

Claves primarias UUID

Todas las tablas de negocio usan id uuid DEFAULT gen_random_uuid(). Las excepciones son herencia del esquema inicial: alerts.id y agent_logs.id son enteros con secuencia. Además hay dos numeradores legibles para humanos, separados de la clave primaria: incidents.number y remote_action_batches.number.

Fechas siempre con zona horaria

No existe ninguna columna timestamp sin zona: todo es timestamptz. created_at tiene default CURRENT_TIMESTAMP; updated_at lo mantiene la aplicación en cada actualización (no hay trigger).

Aislamiento multi-cliente por client_id

Las tablas que pertenecen a un cliente llevan client_id con foreign key a clients. Tres tablas de configuración admiten client_id NULL con el significado "valor global, aplica a todos los clientes": custom_field_defs, incident_rules y message_templates. Como PostgreSQL no considera iguales dos NULL en un índice único, la unicidad "una regla por cliente y clase" se garantiza con un índice sobre COALESCE(client_id, uuid-cero).

Política de borrado según el tipo de relación

3. Convenciones Transversales

Enumeraciones como CHECK, no como tipo ENUM

Los estados (status, severity, origin, kind, role) son columnas de texto con un CHECK (columna IN (...)). Agregar un valor es una migración normal y reversible; con un ENUM de PostgreSQL no se puede quitar un valor ni agregarlo dentro de la misma transacción que lo usa.

Checks de coherencia

Además de los enumerados, hay constraints que atan un estado a su marca de tiempo para que la base no admita registros contradictorios: un incidente está closed si y sólo si tiene closed_at; un pedido de insumo está en estado terminal si y sólo si tiene closed_at; un equipo fusionado tiene merged_into y merged_at a la vez, y nunca apunta a sí mismo; un equipo ignorado tiene ignored_at; un equipo dado de baja no puede estar además fusionado.

Índices parciales para "lo abierto"

Los listados operativos consultan casi siempre lo pendiente, no el histórico. Por eso abundan los índices con WHERE status <> 'closed', WHERE resolved = false o WHERE resolved_at IS NULL: son chicos y cubren exactamente la consulta caliente. Varios son además únicos, y funcionan como regla de negocio garantizada por la base:

ReglaÍndice
Una sola alerta abierta por equipo y tipo (y por agente y tipo)alerts_device_type_open_uniq, alerts_agent_type_open_uniq
Un solo incidente automático abierto por equipo y claseincidents_open_device_class_uniq
Un solo pedido automático abierto por equipo e insumosupply_requests_open_uniq
Un solo cierre vigente por cliente y períodoreport_closures_client_period_open_uniq

JSONB para lo que no se filtra por columna

metadata, payload, params, recipients, custom_data, supplies_details, snmp_credentials, business_hours, discovery_state. Sólo devices.custom_data tiene índice GIN, porque es el único que se filtra desde el portal.

Snapshots desnormalizados a propósito

incidents, supply_requests y report_closure_lines guardan device_serial, device_label, device_model o agent_name además del device_id. Es intencional: un ticket o una línea de facturación debe conservar el nombre que tenía el equipo en ese momento, aunque después se renombre, se fusione o se borre.

4. Tenancy, Usuarios y Acceso

4. Tenancy, Usuarios y Acceso

clients

El tenant. Además de datos de contacto, concentra la configuración por cliente: device_approval_required (los equipos nuevos quedan pendientes hasta que alguien los apruebe), supply_requests_enabled y supply_request_threshold_pct (pedidos automáticos de insumos, umbral entre 1 y 99 %), notification_email, notification_webhook_url y notification_events (qué eventos se notifican), sftp_destination (entrega de reportes) y last_alert_digest_sent_at (control del resumen diario de alertas).

users y user_recovery_codes

Usuarios del portal. role es admin, operator o client_viewer. client_id es nullable: administradores y operadores son globales, pero un client_viewer debe tener cliente, y eso lo exige un CHECK. El segundo factor vive en totp_secret, totp_enabled y totp_required. Los códigos de recuperación se guardan en user_recovery_codes, uno por fila y sólo como hash, con used_at marcando el consumo.

api_keys y api_webhooks

Claves de la API pública, por cliente. Se guarda sólo el hash de la clave (único) y un prefijo de 12 caracteres para identificarla en la interfaz; revoked_at y expires_at la invalidan sin borrarla. Cada cliente tiene como máximo un webhook (client_id es único en api_webhooks), con la lista de eventos suscriptos y un secreto para firmar el envío.

audit_logs

Bitácora de acciones humanas: quién, qué acción, sobre qué objetivo, con qué metadata y desde qué IP. target_id es texto sin foreign key porque apunta a cualquier tabla (patrón polimórfico), y user_id tampoco la tiene para que el registro sobreviva al borrado del usuario. Está indexada por acción, por cliente y por objetivo.

system_settings

Configuración global de una sola fila: la clave primaria es un booleano con CHECK (id), así que sólo puede existir la fila true. Guarda los umbrales de "fuera de línea" para agentes y equipos (1 a 1440 minutos), la configuración SMTP (la contraseña cifrada por la aplicación) y los umbrales globales de insumos.

Tablas menores del dominio: activity_saved_views (filtros guardados de la pantalla de actividad, por usuario) y user_feedback (reportes de error o mejora enviados desde el portal, con estado open / in_progress / closed).

5. Agentes y Acciones Remotas

5. Agentes y Acciones Remotas

agents

El servicio instalado en la red del cliente. Nace con una activation_key única y una fecha de vencimiento; al activarse queda ligado a un hardware_id y recibe su secreto JWT y el hash del refresh token. client_id es nullable porque el agente puede existir antes de asignarse a un cliente.

La configuración operativa que baja al agente vive en la misma fila: rangos IP a escanear, comunidad y credenciales SNMP (con un contador de revisión para detectar cambios), intervalos de escaneo y monitoreo, horario laboral, umbrales de tóner, acceso remoto al panel web de la impresora y canal de actualizaciones. La telemetría del host (versión, nombre, sistema operativo, IP, uptime, último contacto, estado del descubrimiento) también.

El único trigger de la base: agents_client_id_sync. Si se cambia el cliente de un agente, la función sync_devices_client_id() actualiza el client_id de todos sus equipos en la misma transacción. Existe porque devices.client_id es obligatorio y se usa en todos los filtros de aislamiento entre clientes: dejar equipos apuntando al cliente anterior sería una fuga de datos entre tenants.

agent_commands y agent_logs

agent_commands es la cola de comandos hacia un agente: tipo, payload, estado (por defecto pending), resultado, y cuándo se envió y se ejecutó. created_by es texto y no foreign key porque también los crean procesos automáticos. agent_logs guarda los logs que sube el agente, indexados por agente y fecha.

agent_releases

Catálogo de versiones publicadas del agente para la actualización remota: versión y canal únicos, tipo, URL de descarga y sha256 para verificar el binario. Es global, sin foreign keys.

remote_action_batches y remote_action_items

Acciones remotas masivas (RESCAN, FORCE_SCAN, RESTART, FORCE_UPDATE, RESTART_PRINTER). El lote tiene fecha programada, estado y un número legible. Cada ítem apunta a un agente y opcionalmente a un equipo; cuando se despacha queda enlazado al comando generado en agent_commands. Un índice único impide repetir el mismo destino dentro de un lote.

6. Dispositivos

6. Dispositivos

devices: la tabla central

La impresora. Es la tabla más ancha del esquema (74 columnas) y la más consultada. Conviene leerla en capas:

CapaColumnas
Identidad y redserial_number, mac (tipo macaddr), ip_address (tipo inet), hostname, brand, model, sku, firmware, agent_id, client_id (obligatorio).
Nombre y ubicación en tres columnas*_reported (lo que dice la impresora), *_override (lo que cargó un operador) y la columna efectiva (name, location, asset_number), que la aplicación resuelve como "override si existe, si no reported".
Último estado conocidoContadores de páginas (bigint), niveles de tóner por color, last_seen, y 20 columnas cartridge_*: para cada color (negro, cian, magenta, amarillo) el código, serial, capacidad, páginas impresas y estimadas del cartucho. supplies_details (JSON) cubre los insumos que no son los cuatro colores: tambores, fusor, kits.
Estados de gestiónregistration_state (pending / registered / ignored), monitor_state (full / supplies_only / reports_only / disabled), baja (decommissioned_*), fusión de duplicados (merged_into, clave hacia la misma tabla) y origen de insumos (genuine / non_genuine). Cada estado lleva su fecha, su usuario y su motivo.
Campos personalizadoscustom_data (JSON con índice GIN); las definiciones viven en custom_field_defs.

Índices que importan en devices

El más particular es el único parcial por cliente y serial normalizado: garantiza que no haya dos equipos activos con el mismo serial en un cliente, pero excluye de la regla los seriales basura que devuelven algunas impresoras (vacíos, de menos de 5 caracteres, iguales a la IP, caracteres repetidos, "unknown") y los equipos ya fusionados. También hay índices por agente + IP, por cliente + MAC, por cliente + etiqueta de activo, y parciales para los equipos pendientes de aprobación, los que no están en monitoreo completo y los fusionados.

6. Dispositivos

device_models

Catálogo de modelos según hoja de datos: marca, clave de modelo normalizada, nombre a mostrar, ciclo de trabajo mensual, volumen recomendado y si es color. Único por marca y modelo. No tiene foreign key desde devices: el cruce se hace por texto (marca más modelo normalizado), porque el modelo llega tal cual lo reporta la impresora y no siempre está catalogado. La sección 11 desarrolla esta decisión.

device_costs

Costos por equipo en relación uno a uno (device_id es la clave primaria): costo de capital, alquiler trimestral, costo por página mono y color, contrato de servicio y su duración en años (1 a 20), moneda (por defecto ARS). Todos los importes son numeric con un CHECK de no negativos.

device_merge_candidates

Sospechas de equipos duplicados que detecta un proceso automático: cliente, clave de serial, lista de equipos involucrados (array de UUID) y motivo. Sólo puede haber un candidato abierto por cliente y serial; al resolverse queda registrado quién y cuándo.

custom_field_defs

Definiciones de campos personalizados: clave, etiqueta, tipo (text, number, date, select, boolean), opciones para los de selección, posición y fecha de archivo. Con client_id nulo la definición es global. La clave es única por ámbito entre las definiciones no archivadas.

Por qué los tipos de red son nativos

ip_address es inet y mac es macaddr, no texto. PostgreSQL valida el formato al insertar y permite comparar y ordenar correctamente, y el índice por agente + IP evita duplicados por reasignación DHCP.

Fusión de duplicados

Cuando dos filas resultan ser la misma impresora, la absorbida no se borra: queda con merged_into apuntando a la sobreviviente y sale de los listados. Así el histórico de lecturas y tickets de ambas sigue siendo consultable.

7. Lecturas y Series Temporales

7. Lecturas y Series Temporales

readings

Cada lectura SNMP de un equipo: momento, equipo, contadores de páginas, niveles de tóner, si estaba fuera de línea, detalle de insumos en JSON y un reading_id que genera el agente para que reenviar la misma lectura no la duplique.

Es una hypertable de TimescaleDB particionada por tiempo, y por eso no tiene clave primaria: TimescaleDB exige que toda restricción única incluya la columna de partición, y una clave id sola no la incluye. La unicidad real la da el índice único sobre (reading_id, time). Al 12 de septiembre de 2026 hay unas 27.000 lecturas desde el 28 de mayo.

Política activaValor
CompresiónLos bloques con más de 7 días se comprimen, ordenados por tiempo descendente. Reduce el espacio en disco del histórico sin cambiar cómo se consulta.
RetenciónLas lecturas con más de 2 años se eliminan automáticamente.
ÍndicesPor equipo y tiempo descendente, y por tiempo descendente.

readings_daily_agg y readings_monthly_agg

Son agregados continuos de TimescaleDB; por eso DBeaver los muestra como vistas y su definición contiene un UNION ALL contra una tabla interna materializada. Por equipo y día (o mes) guardan el último valor de cada contador, no la suma, porque los contadores de una impresora son acumulativos. Se refrescan solos: el diario recalcula los últimos 3 días, el mensual los últimos 3 meses.

device_usage_30d

Vista SQL común sobre el agregado diario: páginas impresas en los últimos 30 días por equipo, calculadas como diferencia entre días consecutivos y descartando diferencias negativas (reinicio de contador).

Detalle al revisar con DBeaver: las estadísticas de PostgreSQL muestran 0 filas para readings. No es un error: los datos viven en los bloques internos de TimescaleDB (_timescaledb_internal), no en la tabla madre. Un SELECT count(*) devuelve el valor real.

8. Alertas e Incidentes

8. Alertas e Incidentes

alerts

Alerta automática sobre un equipo o sobre un agente; un CHECK exige al menos uno de los dos. Tiene tipo, severidad (warning / critical), valor medido, mensaje, clase y motivo, y su origen (por defecto cloud; también puede generarla el agente). El ciclo de vida es reconocimiento (quién y cuándo) y resolución. La clave primaria es entera, herencia del esquema inicial.

Dos índices únicos parciales impiden que el proceso que evalúa las lecturas genere duplicados: sólo puede haber una alerta abierta por equipo y tipo, y una por agente y tipo.

incidents

El ticket de trabajo. Tiene un número correlativo legible, un identificador externo para el sistema de tickets del cliente, clase, título, descripción, severidad, estado (open, in_progress, on_hold, closed) y origen (auto / manual). Para el SLA guarda apertura, primera respuesta y vencimiento; para el cierre, fecha, usuario, motivo y cantidad de reaperturas. Referencia al equipo, al agente y a la regla que lo generó con SET NULL, y conserva serial y etiqueta del equipo como snapshot. Sólo puede haber un incidente automático abierto por equipo y clase.

incident_alerts

Tabla intermedia de muchos a muchos entre incidentes y alertas, con clave primaria compuesta y auditoría de quién vinculó y cuándo. Un incidente agrupa varias alertas; una alerta puede haber pasado por más de un incidente.

incident_events

Historial del incidente: comentarios, cambios de estado, asignaciones, vinculación y desvinculación de alertas, cambio de identificador externo, reapertura y vencimiento de SLA. Cada evento lleva cuerpo, metadata y usuario.

incident_rules

Reglas de apertura automática por clase de alerta: habilitada o no, severidad mínima, minutos de espera antes de abrir, horas de SLA y cierre automático cuando se resuelven las alertas. Con client_id nulo la regla es global; hay una sola regla por ámbito y clase.

9. Insumos y Cierres

9. Insumos y Cierres de Facturación

supply_requests y supply_request_events

Pedido de insumo (tóner, tambor, etc.) por equipo: identificador estable del insumo dentro del equipo, tipo, color, descripción, SKU, nivel porcentual y días restantes al momento de abrirlo. Estados: pending, reviewed, processed, completed, ignored, cancelled; los tres últimos son terminales y un CHECK exige que tengan closed_at. Origen automático o manual. Sólo puede haber un pedido automático abierto por equipo e insumo. El historial (cambios de estado, comentarios, cierre automático) vive en supply_request_events, con el mismo patrón que los eventos de incidente.

report_closures

Cierre mensual de contadores por cliente: período (primer día del mes), estado, totales agregados (páginas totales, mono, color, otras, cantidad de equipos y de anomalías), y quién cerró y cuándo. Si se reabre, quedan la fecha, el usuario y el motivo, y superseded_by apunta al cierre que lo reemplazó, así la cadena de versiones es trazable. Sólo puede haber un cierre vigente por cliente y período.

Única relación RESTRICT del esquema: report_closures.client_id. Un cliente con cierres de facturación no se puede borrar. Los cierres son registros contables y sobreviven a cualquier operación administrativa sobre el cliente.

report_closure_lines

Una línea por equipo dentro del cierre: primera y última lectura del período con sus contadores, diferencias calculadas (total, mono, color, otras), diferencia estimada cuando hubo huecos de lectura, fuente del dato y si hubo reinicio de contador. Guarda un snapshot completo del equipo y del agente (serial, modelo, marca, nombre del agente) porque el cierre tiene que poder reimprimirse idéntico dentro de un año, aunque el equipo ya no exista.

10. Reportes e Infraestructura

10. Reportes, Notificaciones e Infraestructura

scheduled_reports

Reportes programados por cliente. Tipos: uso, equipos no contactables, niveles de consumibles, listado de activos, historial de alertas, cierre de facturación y exportación de auditoría. Formato CSV o XLSX. Frecuencia none, daily, weekdays, weekly o monthly, con día de la semana (0 a 6), día del mes (1 a 28, para que exista en todos los meses) y hora (0 a 23), todo validado por CHECK. Guarda destinatarios, próxima y última ejecución con su resultado. Un índice parcial por next_run_at sobre los habilitados es lo único que consulta el planificador.

message_templates

Plantillas de asunto y cuerpo por evento: alerta creada, incidente creado, pedido de insumo creado y completado, cierre publicado y resumen de alertas. Con client_id nulo la plantilla es global; hay una por ámbito y evento.

email_log

Registro de cada correo intentado: evento, destinatario, asunto, estado (sent, error, skipped_no_transport, skipped_no_recipient), error y metadata. Permite diagnosticar "no me llegó el mail" sin acceder al servidor SMTP.

knex_migrations y knex_migrations_lock

Tablas internas de la herramienta de migraciones: qué migraciones se aplicaron y en qué lote, y un candado para que dos instancias de la API no migren a la vez. No se editan a mano.

Cómo cambia el esquema

Cada cambio es un archivo de migración versionado con su reversa. La API los aplica al arrancar, en orden, dentro de una transacción. El esquema de producción es siempre el resultado de esa secuencia, reproducible desde cero en cualquier entorno.

Qué no hay en la base

No hay procedimientos almacenados, ni lógica de negocio en SQL, ni triggers salvo el de sincronización de cliente. Las validaciones que la base sí impone (checks, unicidad) son las que un fallo de la aplicación no debe poder saltarse.

11. Decisiones de Diseño

11. Decisiones de Diseño y su Justificación

Las preguntas que suele hacer un administrador de bases de datos al ver el DER por primera vez, con la respuesta.

¿Por qué devices tiene 74 columnas, 20 de ellas cartridge_*?

Porque devices es un snapshot del último estado, pensado para que el listado principal del portal (cientos de equipos, filtrado y ordenado por cualquier columna) se resuelva con un solo SELECT sin joins ni agregaciones. El histórico verdadero está en readings. La alternativa normalizada, una tabla de insumos con una fila por color, obligaría a un join o a una tabla pivote en la consulta más frecuente del sistema. Los insumos que no son los cuatro colores clásicos van al JSON supplies_details, así la tabla no sigue creciendo por cada tipo nuevo.

¿Por qué readings no tiene clave primaria?

Es una hypertable de TimescaleDB particionada por tiempo, y TimescaleDB no permite una clave primaria que no incluya la columna de partición. La idempotencia se garantiza con el índice único sobre (reading_id, time). La migración del 21 de agosto de 2026 documenta el cambio.

¿Por qué device_models no tiene foreign key desde devices?

El modelo llega como texto libre desde la impresora y el catálogo se carga aparte y de forma incompleta. Una foreign key obligaría a catalogar el modelo antes de registrar el equipo, o a dejar la columna vacía casi siempre. El cruce por marca y modelo normalizado, con índice único, da el mismo resultado en la práctica. Si el catálogo llega a ser completo, agregar una columna model_id opcional con foreign key es una migración chica.

¿Por qué hay columnas repetidas en incidentes, pedidos y cierres?

Son snapshots deliberados. Un ticket o una línea de facturación tiene que mostrar lo que decía el equipo en ese momento, no lo que dice hoy, y tiene que sobrevivir a que el equipo se fusione o se borre.

¿Por qué audit_logs.target_id es texto y no foreign key?

Porque apunta a cualquier entidad: equipo, usuario, cliente, regla. Una foreign key por tabla posible sería una columna opcional por cada una. El patrón polimórfico es el estándar en tablas de auditoría, y el índice sobre target_id cubre la consulta "todo lo que pasó con X".

11. Decisiones de Diseño

¿Por qué UUID y no enteros?

Los agentes generan identificadores sin conexión (reading_id) y las entidades aparecen en URLs del portal y de la API: un UUID no es enumerable ni adivinable. alerts y agent_logs quedaron con enteros del esquema inicial; cambiarlos no aporta y rompería la clave compuesta de incident_alerts.

¿Por qué los estados son CHECK y no ENUM?

Agregar un valor a un ENUM de PostgreSQL no puede hacerse dentro de la misma transacción que lo usa, y no se puede quitar un valor. Con CHECK, cada cambio es una migración normal y reversible.

¿Por qué tanto índice parcial y único?

Los únicos parciales son reglas de negocio que la aplicación no puede garantizar sola cuando dos procesos o dos réplicas de la API escriben a la vez: "una alerta abierta por equipo y tipo", "un cierre vigente por período". Que lo garantice la base es más barato y más seguro que un bloqueo en código.

¿Por qué system_settings.id es un booleano?

Es la forma canónica de tabla de una sola fila en PostgreSQL: clave primaria booleana con CHECK (id) sólo admite la fila true. Evita un LIMIT 1 implícito y que alguien inserte una segunda fila.

¿Por qué hay un trigger si el resto de la lógica está en la aplicación?

devices.client_id es obligatorio y se usa en todos los filtros de aislamiento entre clientes. Si reasignar un agente dejara sus equipos con el cliente anterior, sería una fuga de datos entre tenants. El trigger hace esa actualización de forma atómica, en la misma transacción, sin importar por dónde se haga el cambio.

Puntos abiertos conocidos

No son errores, pero un revisor los va a señalar y conviene tener la respuesta lista:

  • agent_commands.created_by es texto, no foreign key a users, porque también lo crean procesos automáticos.
  • audit_logs.user_id no tiene foreign key, por la misma razón que target_id: el log debe sobrevivir al borrado del usuario.
  • No hay trigger de updated_at; lo mantiene la aplicación en cada actualización.
  • readings.device_id admite nulo. No debería haber lecturas sin equipo; hoy lo garantiza la aplicación, no la base.

12. Cómo Verificar el Esquema con DBeaver o SQL

Todas las cifras de este documento se regeneran con consultas de sólo lectura al catálogo de PostgreSQL. Cualquier revisor puede ejecutarlas desde DBeaver para confirmar que lo descripto coincide con la base que tiene delante.

Tablas y vistas del schema public
SELECT c.relname, c.relkind
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind IN ('r','v','m') ORDER BY 1;
Foreign keys con su política de borrado (c = cascade, n = set null, r = restrict)
SELECT conrelid::regclass AS tabla, a.attname AS columna,
       confrelid::regclass AS referencia, confdeltype AS on_delete
FROM pg_constraint c
JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = ANY (c.conkey)
WHERE contype = 'f' AND connamespace = 'public'::regnamespace ORDER BY 1, 2;
Checks (los "enums" del esquema) e índices parciales
SELECT conrelid::regclass, conname, pg_get_constraintdef(oid)
FROM pg_constraint WHERE contype = 'c' AND connamespace = 'public'::regnamespace;

SELECT tablename, indexname, indexdef FROM pg_indexes
WHERE schemaname = 'public' AND indexdef LIKE '%WHERE%' ORDER BY 1;
Estado de TimescaleDB y migraciones aplicadas
SELECT hypertable_name, compression_enabled FROM timescaledb_information.hypertables;
SELECT hypertable_name, proc_name, config FROM timescaledb_information.jobs
WHERE hypertable_name IS NOT NULL;
SELECT name, batch, migration_time FROM knex_migrations ORDER BY id DESC LIMIT 5;
