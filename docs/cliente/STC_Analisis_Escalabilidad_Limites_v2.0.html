1. Resumen Ejecutivo

STC Cloud corre self-hosted en Docker sobre un servidor propio (VPS): todo el stack (Portal, API, PostgreSQL/TimescaleDB, Redis, reverse proxy con SSL) está orquestado por `docker-compose.prod.yml` y `deploy.sh` (ver `docs/internos/DEPLOY_CLOUD.md`). El techo de capacidad depende de dos cosas: el hardware real del VPS (CPU/RAM/disco) y cómo el código maneja la concurrencia cuando escala a una base de 200+ clientes reales, con varios agentes por cliente y miles de dispositivos monitoreados en conjunto.

Este documento responde tres preguntas, en ese orden: cómo está hecha la infraestructura (§2), cómo se comporta bajo carga concurrente — qué mecanismos tiene el código para sostener el escenario objetivo de 200+ clientes, varios agentes por cliente y miles de equipos sincronizando cada ~5 minutos (§3) — y cómo escala: qué servidor hace falta y cuál es el camino de crecimiento previsto si la flota sigue creciendo (§4).

2. Infraestructura

2. Cómo Está Hecho: Self-Hosted en Docker

Los tres niveles lógicos del sistema (Portal, API, base de datos) corren en el mismo servidor propio, cada uno en su contenedor Docker, orquestados por docker-compose.prod.yml. El almacenamiento depende del disco real del servidor — típicamente decenas o cientos de GB en un VPS estándar, dimensionado para el volumen de datos que generan miles de dispositivos reportando contadores periódicamente.

Contenedor Límite configurado hoy Rol Margen para 200+ clientes
api 512 MB RAM / 1 CPU Backend Fastify — WS persistente por agente, sync cada ~5 min, dashboard/reportes del portal. SÍ — con los mecanismos de §3
postgres 1 GB RAM / 1 CPU PostgreSQL 16 + TimescaleDB, con compresión y retención configuradas sobre `readings`. SÍ — pool de 20 conexiones (ver §3)
redis 256 MB RAM / 0.5 CPU Rate-limit store, blacklist de tokens de agente, 4 colas BullMQ (notificaciones, cierres, webhooks públicos, evaluación de alertas). SÍ — volumen estimado muy por debajo de este límite
portal 128 MB RAM / 0.25 CPU Build estático de React servido por nginx dentro del contenedor. SÍ — es un sitio estático, no procesa nada por request
nginx / certbot / backup 128 MB / 64 MB / 256 MB Reverse proxy + SSL automático (Let's Encrypt), y `pg_dump` diario con retención de 30 días. SÍ

Cuál es el techo real

En un servidor propio el techo de capacidad lo define una sola cosa: que el código esté escrito para aprovechar bien los recursos del servidor bajo carga concurrente real, con miles de dispositivos sincronizando en paralelo. Los mecanismos que lo garantizan se describen en §3.

3. Comportamiento Bajo Carga

3. Cómo Funciona Bajo Carga Concurrente

Mecanismos con los que el backend sostiene el escenario objetivo — 200+ clientes, varios agentes por cliente, miles de dispositivos sincronizando cada ~5 minutos — sin degradarse:

Pool de conexiones a la base de datos

El pool de Knex es configurable por variables de entorno (`DB_POOL_MIN`/`DB_POOL_MAX`), con un default de 20 conexiones — suficiente para absorber los picos de sincronización concurrente más el tráfico del portal, con margen amplio frente al `max_connections` default de Postgres (100).

Ingesta de lecturas con integridad de facturación

`POST /devices/sync` — la ruta que recibe el tráfico masivo de los agentes — procesa cada dispositivo del lote en su propia transacción con `pg_advisory_xact_lock`: si dos agentes del mismo cliente ven la misma impresora en paralelo, las escrituras se serializan y no se pisan. El INSERT final de lecturas es bulk. Este diseño prioriza la integridad de los datos que alimentan la facturación mensual (resolución de identidad del dispositivo, detección de reset de contador, fusión de duplicados, apertura de alertas) por sobre el throughput bruto — y el throughput resultante cubre con margen la escala objetivo.

Techos de seguridad en los listados del portal

`GET /agents` y `GET /clients` tienen un techo de 2.000 filas y `GET /devices` de 5.000 — ninguna pantalla puede pedir una transferencia sin límite aunque la flota crezca. `Alerts`, `Reports` y el `Dashboard` van más allá: paginan o agregan del lado del servidor (COUNT/SUM), y nunca traen listas completas al navegador.

Rate limiting por identidad de agente

`/devices/sync` y `/agents/:id/heartbeat` tienen un límite propio de 20 req/min por agente, identificado por su token — no por IP. Varios agentes de un mismo cliente saliendo por la misma IP corporativa (NAT compartido) no compiten entre sí ni con el tráfico del portal: cada uno tiene su propio cupo. La API pública usa el mismo patrón por API key.

Reconexión escalonada de los agentes

El backoff de reconexión WS del agente (`SocketManager.ts`) es exponencial (5s → techo de 300s) con jitter de ±30% en cada escalón: si el backend se reinicia con 200+ agentes conectados, las reconexiones se distribuyen en el tiempo en vez de llegar todas en oleadas sincronizadas.

Base de datos diseñada para series temporales

  • TimescaleDB: `readings` es hypertable con compresión activa (7 días) y retención de 24 meses; agregados continuos diarios/mensuales para tendencias sin pegarle al dato crudo.
  • Índices: cobertura en las tablas calientes (`readings`, `devices`, `alerts`, `agents`) para los patrones de consulta reales.
  • Colas BullMQ: con 200 clientes sincronizando cada 5 min, el volumen de jobs/minuto queda muy por debajo de cualquier umbral que preocupe.

4. Sizing y Crecimiento

4. Cómo Escala: Sizing del Servidor y Camino de Crecimiento

Dos cosas definen la escalabilidad práctica: dimensionar bien el servidor para la escala objetivo, y saber de antemano cuál es el camino de evolución si la flota sigue creciendo más allá de eso.

1. Sizing recomendado del VPS para 200+ clientes

Recurso Mínimo recomendado Motivo
vCPU 4 vCPU Los límites actuales de `docker-compose.prod.yml` suman ~3.5 CPU entre todos los contenedores (api 1.0 + postgres 1.0 + redis 0.5 + portal 0.25 + nginx 0.25 + certbot 0.1 + backup 0.5) — 4 vCPU deja margen real, no sólo lo justo.
RAM 4-8 GB Suma de límites actuales ~2.3 GB + margen del sistema operativo y picos de Postgres bajo el pool de 20 conexiones (cada conexión de Postgres tiene su propio costo de memoria en el lado del servidor, no sólo del lado del pool de Knex).
Disco ≥100 GB SSD La compresión de TimescaleDB reduce mucho el tamaño de `readings`, pero el volumen real depende del número final de dispositivos monitoreados — monitorear el crecimiento real del volumen `pgdata` durante los primeros meses en vez de asumir un número, y dejar margen para los backups diarios (`pg_dump`, 30 días de retención) que viven en un volumen aparte.

2. Qué monitorear en producción

  • Crecimiento del disco: el volumen `pgdata` durante los primeros meses de operación real — la compresión de TimescaleDB hace difícil predecirlo en papel; medirlo es más confiable que asumirlo.
  • CPU/RAM en picos de sincronización: los contenedores tienen límites explícitos en `docker-compose.prod.yml`; si `api` o `postgres` los tocan de forma sostenida, es la señal para subir el sizing.
  • Stack de observabilidad opcional: el mismo `docker-compose.prod.yml` incluye un perfil `observability` (Prometheus + Grafana + Alertmanager) con alertas ya definidas sobre caída de la API, tasa de errores 5xx y jobs internos sin ejecutar — se activa con `--profile observability`, sin instalar nada extra.

3. Camino de evolución si la flota crece más allá del objetivo

  1. Paginación real en los listados: los techos actuales (2.000/5.000 filas) cubren la escala objetivo; superado ese volumen, el paso natural es paginación con controles de página en las pantallas de agentes, clientes y dispositivos.
  2. Batching agregado en la ingesta: el procesamiento por dispositivo de `/devices/sync` prioriza integridad de facturación; si el volumen de ingesta creciera un orden de magnitud, la evolución es agregar la resolución de identidad en lotes — un cambio de esfuerzo alto que sólo se justifica a esa escala.
  3. Réplicas horizontales de la API: la capa de WebSocket ya está preparada para múltiples réplicas (retransmisión entre procesos vía Redis pub/sub); escalar horizontalmente requiere además ajustar el pool de base de datos por réplica y migrar los jobs de temporizador simple a colas — el diseño actual ya lo contempla.
Conclusión: la escala objetivo de 200+ clientes y miles de equipos está cubierta por el diseño y el sizing actuales. El crecimiento posterior tiene un camino de evolución conocido y ordenado — no hay ningún punto del sistema que requiera un rediseño para crecer.
