1. Ciclo de Vida del Agente

1. Ciclo de Vida del Agente

El agente (main.ts) es un proceso Node.js compilado como ejecutable único mediante pkg y registrado como servicio de Windows a través de NSSM. Su operación se divide en tres loops independientes que corren de manera concurrente pero sin bloqueos entre sí.

Flujo de Inicialización y Loops
  main()
    │
    ├─► openQueue()          — Abre/crea SQLite (WAL mode). Migra columnas en caliente.
    ├─► loadConfig()         — Descifra config.enc con HWID binding (AES-256-GCM).
    ├─► waitForConnectivity() — Backoff exponencial 10s → 5min hasta alcanzar servidor.
    ├─► connectWebSocket()   — Establece canal WSS persistente con el portal en la nube.
    │
    ├─── LOOP A: Scan  ─────────────────────────────────────────────────────────────┐
    │    Cada N minutos (configurable por schedule o intervalo fijo)                 │
    │    snmpScan(ipRanges, community)                                               │
    │      └─► Para cada IP en rangos: readDevice(ip, community, hintMethod?)       │
    │            └─► enqueueReading(result) → SQLite                                │
    │                upsertKnownDevice(ip, { pollMethod }) → SQLite                 │
    └─── LOOP B: Sync  ─────────────────────────────────────────────────────────────┘
         Cada 30 segundos (si hay conectividad WAN)
         getPendingReadings() → POST /api/readings → markSynced()
         Purga registros vencidos (> 7 días) o ya sincronizados.

A. Startup y Configuración Cifrada

Al arrancar, el agente extrae el Hardware ID del equipo local combinando el MachineGuid del registro de Windows con el serial de BIOS vía WMI. Aplica SHA-256 sobre la concatenación y deriva una clave AES-256 mediante PBKDF2 (100 000 iteraciones). Con esa clave descifra config.enc, obteniendo la URL del servidor, el agentId, los rangos IP a escanear y la comunidad SNMP.

Integridad de Máquina: Si el archivo config.enc se copia a otro equipo, el HWID resultante difiere y el tag de autenticación GCM falla, disparando HWID_MISMATCH y abortando la ejecución antes de cualquier conexión de red.

B. Conectividad WAN y WebSocket

La función waitForConnectivity() ejecuta un backoff exponencial: comienza con 10 s de espera, duplica cada intento y se limita a un techo de 5 minutos. Una vez establecida la conectividad, abre un canal WebSocket Seguro (WSS port 443) con el portal para recibir comandos en tiempo real (forzar scan, actualizar configuración). El canal se reconecta automáticamente ante pérdidas de red.

C. Scheduler de Escaneo

El agente corre 3 loops independientes que se autorregulan según el horario laboral configurable del sitio (días de la semana, hora de inicio/fin y zona horaria IANA — configurable por agente desde el portal):

Dentro del horario laboral

Discovery cada 10 min, contadores cada 20 min, insumos cada 60 min.

Fuera del horario laboral

Discovery cada 60 min, contadores e insumos cada 4 horas — reduce carga de red fuera de horario sin dejar de monitorear.

2. Detección de Puertos

2. Detección de Puertos y Precalificación de Hosts

Antes de interrogar a cualquier dispositivo, el agente ejecuta una sonda TCP paralela en cuatro puertos clave. Este paso decide qué protocolos están disponibles y, fundamentalmente, si el host es una impresora o infraestructura de red general (router, switch, servidor).

A. Parámetros de Tiempo y Concurrencia

Constante Valor Aplica a Motivo
REACH_TIMEOUT 500 ms Puertos 9100, 631 Puertos exclusivos de impresión: respuesta casi instantánea o cerrados.
WEB_REACH_TIMEOUT Fix Mayo 2026 2 000 ms Puertos 80, 443 Firmware EWS antiguo (Samsung SyncThru V4/V5) puede tardar >500 ms en aceptar el TCP handshake aunque el puerto esté abierto.
MAX_CONCURRENT 20 Sesiones SNMP Semáforo interno que limita sesiones SNMP simultáneas para no saturar el switch.
CONCURRENCY_LIMIT 10 Workers de scan Máximo de IPs interrogadas en paralelo dentro de snmpScan().

B. Lógica de checkOpenPorts()

Las cuatro sondas TCP se lanzan en paralelo con Promise.all. Si el socket conecta (connect event), el puerto se marca abierto. Si ocurre ECONNREFUSED, se considera abierto (el host respondió, aunque rechazó). Cualquier otro error o timeout devuelve cerrado. 

async function checkOpenPorts(ip: string): Promise<Set<number>> {
  const results = await Promise.all(
    PRINTER_PORTS.map(async p => ({
      p,
      open: await tryPort(ip, p, p === 80 || p === 443
              ? WEB_REACH_TIMEOUT   // 2 000 ms — firmware EWS lento
              : REACH_TIMEOUT       //   500 ms — JetDirect / IPP
            ).catch(() => false),
    })),
  );
  return new Set(results.filter(r => r.open).map(r => r.p));
}

C. Bifurcación de Seguridad: hasPrinterPort

Los puertos TCP 9100 (JetDirect/PJL) y 631 (IPP) son exclusivos del protocolo de impresión. Ningún router, switch o servidor convencional los expone. Esta propiedad los convierte en el criterio de seguridad central:

hasPrinterPort = false

El host NO es una impresora confirmada. El agente omite toda petición HTTP/S a puertos 80/443 y recurre únicamente a SNMP con validación de Printer-MIB. Esto evita activar alertas IDS/SIEM por escaneo web no autorizado en equipos de infraestructura.

hasPrinterPort = true

La impresora está confirmada físicamente. El agente queda habilitado para iniciar la cascada completa: EWS + SNMP + PJL + IPP, en ese orden de preferencia.

Antecedente del fix de WEB_REACH_TIMEOUT: Con el timeout original de 500 ms, los modelos Samsung SL-M4072FD y SL-M4020ND (firmware SyncThru V4) no eran detectados con puerto 80 abierto. El agente calculaba hasWebPort = false y nunca intentaba EWS, cayendo siempre a SNMP. Al elevar el timeout a 2 000 ms para los puertos web, el TCP handshake lento de ese firmware queda cubierto y la detección es correcta.

3. Cascada de Descubrimiento

3. Cascada de Descubrimiento (readDevice)

La función readDevice(ip, community, hintMethod?) es el orquestador central. Evalúa los puertos abiertos, aplica el fast path por hint cuando existe, y ejecuta la cascada de protocolos en orden de fidelidad decreciente.

Árbol de decisión de readDevice()
  checkOpenPorts(ip)
       │
       ├─ openPorts.size === 0 ──────────────────────────────────► return null
       │
       ├─ hintMethod conocido? ──► Fast Path / Self-Healing (ver §4)
       │
       ├─ hasPrinterPort === false && hasWebPort === false ──────► readViaSNMP() [solo MIB]
       │
       ├─ hasPrinterPort === false && hasWebPort === true ──────► Caso B (solo web)
       │    readViaSNMP() [validar como impresora]
       │      └─ snmpResult? ──► readViaEWS(ip, brand, model) ──► ews ?? snmpResult
       │
       └─ hasPrinterPort === true ──────────────────────────────► Caso A (impresora confirmada)
            readViaSNMP(ip)  ← [identifica brand + model para optimizar EWS]
              │
              ├─ hasWebPort? ──► readViaEWS(ip, brand, model)
              │                    └─ ews.total_pages !== null ──► return ews ✓
              │
              ├─ snmpResult.total_pages !== null ──────────────► return snmpResult ✓
              │
              ├─ readViaPJL(ip)
              │    └─ pjl.total_pages !== null ───────────────► return pjl ✓
              │
              ├─ readViaIPP(ip)
              │    └─ ipp? ────────────────────────────────────► return ipp ✓
              │
              └─ return snmpResult ?? null  [datos parciales de identidad]

A. Caso A — Impresora Confirmada (hasPrinterPort = true)

El agente primero ejecuta readViaSNMP() en modo liviano para obtener marca y modelo del dispositivo. Esta información se pasa a readViaEWS() para que el motor EWS filtre y ordene sus candidatos de forma óptima (por ejemplo, intentar primero los endpoints Samsung SyncThru en lugar de los Samsung SWS en modelos sin copiadoras). Si EWS devuelve total_pages !== null, la cascada se detiene y se devuelve el resultado EWS. De lo contrario se continúa con SNMP, luego PJL, luego IPP.

B. Caso B — Solo Puerto Web Disponible

Si el host responde al puerto 80 o 443 pero NO a 9100 ni 631, podría ser un router, NAS, teléfono IP o una impresora antigua. El agente primero valida via SNMP consultando la OID hrDeviceType y la Printer-MIB (prtGeneralConfigChanges). Solo si SNMP confirma que es una impresora, se lanza EWS. Esto previene 4–10 segundos de timeouts HTTP en dispositivos de red que no son impresoras.

C. Criterio de Aceptación de Resultados

Cada método devuelve un DeviceReading con el campo total_pages. La cascada avanza al siguiente nivel únicamente si total_pages === null. Un resultado con total_pages = 0 (impresora nueva, sin páginas impresas) sí se acepta como válido y detiene la cascada.

4. Fast Path y Self-Healing

4. Sistema de Hint: Fast Path y Self-Healing

Para evitar la cascada completa en cada ciclo de scan, el agente persiste el método exitoso de la lectura anterior en la columna poll_method de la tabla known_devices en SQLite. Este valor se llama hint y funciona como caché de protocolo por IP.

A. Fast Path (Ruta Rápida)

Al inicio de readDevice(), si existe un hintMethod válido (distinto de 'unknown'), el agente intenta ese método directamente sin ejecutar la cascada: 

if (hintMethod && hintMethod !== 'unknown') {
  const shouldIgnoreHint = hintMethod === 'snmp'
    && (openPorts.has(80) || openPorts.has(443));   // self-healing check

  if (!shouldIgnoreHint) {
    const fast = hintMethod === 'snmp'
      ? await readViaSNMP(ip, community)
      : await readViaMethod(ip, hintMethod);          // EWS / PJL / IPP sin brand/model

    if (fast) {
      if (fast.mono_pages !== null || hintMethod === 'ews') return fast;
    }
    // Si el método falla o no devuelve contadores → cae a cascada completa
  }
}
Condición de retorno del fast path EWS: Cuando el hint es 'ews', el resultado se retorna incluso si mono_pages es null (impresoras monocromáticas sin desglose simplex/dúplex), ya que el campo total_pages puede ser suficiente. Para otros métodos, se exige mono_pages !== null como indicador de lectura rica.

B. Self-Healing: Detección de Degradación a SNMP

Si el método en caché es 'snmp' pero el dispositivo tiene un puerto web abierto (80 o 443), existe la posibilidad de que el agente haya quedado atascado en SNMP por un fallo transitorio anterior de EWS. El flag shouldIgnoreHint detecta esta situación e ignora el hint, forzando la cascada completa para intentar una actualización automática a EWS:

Ciclos de Evolución del poll_method
  CICLO 1 (primer scan, sin hint):
    checkOpenPorts → {80, 631, 9100}   hasWebPort = true, hasPrinterPort = true
    Cascada: SNMP → EWS → EWS exitoso (total_pages = 91 991)
    Resultado: poll_method = 'ews'  ←── almacenado en SQLite

  CICLO 2 (hint = 'ews'):
    shouldIgnoreHint = false   (hint no es 'snmp')
    readViaEWS(ip)  →  EWS exitoso  →  return fast
    Resultado: poll_method = 'ews'  (sin cambio)

  CICLO N (hipótesis: hint = 'snmp' por fallo antiguo, puerto 80 abierto):
    shouldIgnoreHint = TRUE   (hint es 'snmp' Y openPorts.has(80) = true)
    Cascada completa → EWS exitoso → retorna EWS
    Resultado: poll_method actualizado a 'ews'  ←── auto-sanado

C. Actualización del Hint tras cada Scan

Al finalizar cada lectura exitosa, main.ts llama a upsertKnownDevice(ip, { pollMethod: result.poll_method }). La tabla known_devices usa COALESCE en la cláusula ON CONFLICT DO UPDATE, por lo que el método se actualiza solo si el nuevo valor es no-nulo, preservando la última lectura válida ante fallos transitorios.

5. Motor EWS

5. Motor EWS: Transporte, Candidatos y Acumulador

El motor EWS (ews.ts) abstrae la extracción de datos sobre HTTP/S nativo de Node.js. Implementa tres capas: transporte (fetchHttp), lista ordenada de candidatos y un acumulador incremental con cortocircuito.

A. Capa de Transporte (fetchHttp)

Construida sobre los módulos nativos http / https de Node.js. Parámetros clave:

  • EWS_TIMEOUT = 10 000 ms: Timeout de socket (inactividad durante la transferencia de datos). Si la CPU del firmware de la impresora está saturada y deja de enviar datos durante 10 s, el socket se destruye con req.destroy() liberando el Event Loop. Este valor fue elevado desde 4 s para evitar falsos timeouts en scans concurrentes.
  • rejectUnauthorized: false: Omite validación de certificados TLS. Obligatorio para impresoras con certificados auto-firmados o expirados, habituales en entornos corporativos locales.
  • Seguidor de Redirecciones: Maneja códigos 301, 302, 307 y 308 recalculando protocolo y ruta. Límite de 3 saltos para prevenir bucles (portales cautivos).

B. Matriz de Candidatos y Priorización por Fabricante

El motor define 16 endpoints específicos ordenados por fabricante y confiabilidad. Cuando targetBrand es conocido, filtra y reordena los candidatos para ese fabricante:

Fabricante Endpoint Dato principal extraído
Samsung SWS/sws.application/…/homeDeviceInfo.swsModelo, serial, tóner (HTML coreano/inglés)
Samsung SWS/sws.application/…/countersView.swsContadores mono/color (tabla HTML)
Samsung SyncThru/sws/app/information/home/home.jsonModelo y serial (JSON)
Samsung SyncThru/sws/app/information/supplies/supplies.jsonNiveles de tóner por color
Samsung SyncThru/sws/app/information/counters/counters.jsonContadores GXI simplex/dúplex
Lexmark/cgi-bin/dynamic/printer/PrinterStatus.htmlNiveles de tóner
Lexmark/cgi-bin/dynamic/printer/config/reports/deviceinfo.htmlSerial, modelo, total páginas
HP FutureSmart/DevMgmt/ProductUsageDyn.xmlXML estructurado de contadores HP
HP Legacy/hp/device/InternalPages/Index?id=UsagePagePágina de uso (HTML)

Para Samsung, la selección de orden depende del modelo: si el nombre contiene LX, FX o GX (indicativo de copiadora/MFP gama alta), se prueban primero los endpoints SWS. En caso contrario (o si el modelo es desconocido), se prueban primero los endpoints SyncThru, evitando que las 3 peticiones SWS con 404 congestionem la ventana de tiempo disponible en firmware antiguo.

C. Acumulador Incremental y Cortocircuito

El motor itera la lista de candidatos manteniendo un objeto acc que fusiona los resultados de cada endpoint exitoso: un endpoint puede aportar modelo y serial, el siguiente puede aportar tóner, el siguiente los contadores. La fusión es conservadora: solo se sobreescribe un campo si el nuevo valor no es undefined.

Cortocircuito: En el momento en que acc.totalPages !== undefined, el agente rompe el bucle con break y retorna. No se realizan más peticiones HTTP a endpoints restantes, reduciendo el tráfico de red en hasta un 70 % en lecturas completas.

6. Parsers por Fabricante

6. Parsers por Fabricante

Cada endpoint de la matriz tiene asociado un parser dedicado que extrae los campos del cuerpo HTTP (HTML, JSON o JavaScript variable-style) mediante expresiones regulares y lectores de texto plano. No se utiliza ningún motor DOM ni navegador embebido.

A. Samsung SyncThru (firmware V4/V5 — modelos SL-M, SCX, ML, CLP)

El firmware SyncThru devuelve los datos en formato JavaScript de asignación de variables (no JSON estricto). El parser parseSamsungCounters extrae contadores con regex específicas: 

// counters.json — variables JavaScript en texto plano
GXI_BILLING_TOTAL_IMP_CNT       : 91991   → totalPages
GXI_BILLING_SIMPLEX_BW_TOTAL_CNT : 84200  → monoPages (simplex)
GXI_BILLING_DUPLEX_BW_TOTAL_CNT  : 7791   → monoPages (dúplex)
GXI_BILLING_SIMPLEX_COLOR_TOTAL_CNT : 0   → colorPages

// Lógica de cálculo: mono = simplexBw + duplexBw
// Si total no está disponible: total = mono + color
// Fallback final: si no hay simplex/dúplex → mono = total

El parser parseSamsungSyncThruSupplies extrae los niveles de tóner desde bloques toner_black: { remaining: N, id: "...", serial: "...", capa: K }, incluyendo el identificador de cartucho, su serial físico y la capacidad declarada en páginas.

B. Samsung Solution Web Service (SWS — modelos X4300LX, gama copiadora)

Los modelos de copiadora de alta gama usan una interfaz web diferente. parseSamsungSolutionHome extrae el modelo y serial de una tabla HTML bilingüe (coreano/inglés) y los niveles de tóner desde un array JavaScript incrustado: 

var tonerData = [ {cartridge:'검정색', remaining:'90'}, {cartridge:'시안', remaining:'75'}, ... ]
// Mapeado: 검정색/black→K, 시안/cyan→C, 마젠타/magenta→M, 노란/yellow→Y

C. HP (FutureSmart y Legacy)

El parser parseHpXml lee el endpoint ProductUsageDyn.xml extrayendo etiquetas como <dd:TotalImpressions>, <dd:MonochromeImpressions> y bloques de suministros (<dd:ConsumableTypeEnum> para identificar tóner negro/color). Limpia separadores de miles (coma, punto) antes de parsear enteros.

El parser parseHpHtml actúa como fallback extrayendo filas de tabla que contienen cadenas como "Total Impressions" o "Black Cartridge" mediante regex multilingüe.

D. Lexmark

parseLexmarkPrinterStatus extrae los niveles de tóner desde bloques de porcentaje en el HTML de estado. parseLexmarkEws combina la lectura del modelo, serial y total de páginas desde el informe de configuración del dispositivo, buscando patrones como Total Pages Printed o Device Serial Number.

E. Genérico (Ricoh, Brother, Epson, Canon, Konica, Xerox)

El parser parseGeneric ejecuta una búsqueda amplia de patrones comunes: etiquetas con "page count", "total pages", "life count", o contadores en formato numérico adyacente a etiquetas de impresión. Se usa para modelos sin parser dedicado. Solo identifica contadores básicos, sin datos de tóner ni desglose monocolor.

7–8. SQLite y Sincronización

7. Cola SQLite, Backpressure y Retención

El agente mantiene una base de datos SQLite local en C:\ProgramData\STCCloudMonitor\local.db operando en modo Write-Ahead Logging (WAL). La base contiene dos tablas principales:

Tabla Propósito
readings_queue Cola de lecturas pendientes de sincronización. Cada fila almacena todos los campos de telemetría: contadores, tóner, códigos de cartucho, seriales, método de poll. Columna synced marca si fue enviada al servidor.
known_devices Caché de dispositivos conocidos por IP. Almacena brand, model, serial, estado de registro y el poll_method (hint) de la última lectura exitosa.

A. Backpressure

Si la conectividad WAN se interrumpe por un período prolongado, la cola crece. El agente implementa un límite de 10 000 registros pendientes (BACKPRESSURE_LIMIT). Al superarlo, isBackpressureActive() devuelve true y el scan se pausa hasta que el sincronizador vacíe la cola, protegiendo el disco local.

B. Retención y Purga Automática

Cada ciclo de sincronización ejecuta purgeOld(), que elimina registros con synced = 1 o con antigüedad superior a 7 días. Esto mantiene el archivo de base de datos estable y dentro de márgenes predecibles de espacio en disco.

C. Migración en Caliente

Al abrir la base de datos, el agente ejecuta una serie de sentencias ALTER TABLE … ADD COLUMN IF NOT EXISTS envueltas en try/catch. Esto permite agregar nuevas columnas (como los campos de cartucho o el poll_method) sin romper instalaciones existentes, sin gestores de migración externos y sin downtime.

8. Sincronización con la Nube

El loop de sincronización corre cada 30 segundos. Recupera hasta 500 registros con synced = 0, los serializa en JSON y los envía en lote mediante un POST autenticado al endpoint de ingesta del portal.

  • Autenticación JWT: Cada petición lleva un Access Token de corta duración en el header Authorization: Bearer.
  • Rotación de Token: Ante un HTTP 401, el agente dispara tryRefresh() de forma asíncrona: envía el Refresh Token de 64 bytes, recibe una nueva pareja de tokens y los persiste cifrados en config.enc.
  • Reintentos con Proxy: Si está configurado un proxy corporativo (proxyUrl en la config), la sincronización y el WebSocket lo utilizan automáticamente vía HTTP CONNECT tunneling.
  • Idempotencia: El servidor de ingesta procesa los lotes de forma idempotente. Si una petición falla a mitad de camino, los registros no marcados como synced se reenvían en el siguiente ciclo sin duplicar datos en la plataforma.
Garantía de no pérdida de datos: Mientras el disco del equipo tenga espacio, el agente puede operar desconectado de la WAN por hasta 7 días sin perder lecturas. Al reconectarse, el sincronizador drena la cola en orden cronológico, preservando la serie temporal completa en la plataforma.
