1. Qué es el Agente

1. Qué es y Dónde Vive el Agente

El Agente STC Cloud es un proceso Node.js compilado como ejecutable único (sin dependencia de un runtime instalado en el equipo destino) que se instala como servicio de Windows dentro de la red local del cliente, típicamente en un equipo o servidor siempre encendido. No requiere agentes en cada impresora: un único proceso descubre y monitorea todas las impresoras de red visibles desde su segmento.

Ubicación del Agente en la Red del Cliente
  ┌───────────────────────────── Internet ─────────────────────────────┐
  │                                                                     │
  │                        STC Cloud Portal (API + WSS)                │
  │                                                                     │
  └───────────────────────────────┬─────────────────────────────────────┘
                                    │  HTTPS / WSS — únicamente saliente
  ┌─────────────────────────────── │ ─────────────────── Red del Cliente ┐
  │                                 ▼                                    │
  │                     ┌───────────────────────┐                        │
  │                     │   STC Cloud Agent      │  Windows Service       │
  │                     │  (proceso único, Node) │                        │
  │                     └───────────┬────────────┘                        │
  │                                 │ SNMP / HTTP(S) / PJL / IPP           │
  │              ┌──────────────────┼──────────────────┐                  │
  │              ▼                  ▼                  ▼                  │
  │        ┌───────────┐      ┌───────────┐      ┌───────────┐            │
  │        │ Impresora │      │ Impresora │      │ Impresora │   ...      │
  │        └───────────┘      └───────────┘      └───────────┘            │
  └────────────────────────────────────────────────────────────────────┘

El agente no expone ningún servicio hacia la red: es un cliente puro que sale a buscar datos a las impresoras (SNMP/HTTP/PJL/IPP) y sale a entregarlos a la nube (HTTPS/WSS). Esta dirección única del tráfico es la base de su modelo de seguridad, detallado en la sección 3.

Componentes Internos Principales

Módulo Responsabilidad
core/Orquestación: ciclo de vida, scheduler, configuración cifrada, conexión WebSocket, comandos remotos.
capture/Motor de captura: identifica el dispositivo, resuelve su perfil de modelo o familia de protocolo, y recolecta identidad, contadores, insumos, alertas y bandejas. Un archivo declarativo por modelo, con familias compartidas y Printer-MIB como red de seguridad.
capture/transport/Transportes de bajo nivel usados por el motor: HTTP/S (para EWS) y SNMP.
snmp/Parsers de EWS por fabricante y utilidades de protocolo (PJL, IPP, OIDs) que el motor de captura reutiliza.
sync/Cola local SQLite y subida por lotes al portal en la nube.
install/Instalación/desinstalación como servicio de Windows (integración NSSM).

2. Los Tres Loops

2. Los Tres Loops: Scan, Sync y Canal en Tiempo Real

Tras el arranque (main.ts), el agente corre tres ciclos concurrentes e independientes que no se bloquean entre sí:

Ciclos de Operación
  main()
    ├─► openQueue()           — Abre SQLite local en modo WAL
    ├─► loadConfig()          — Descifra config.enc (HWID binding)
    ├─► waitForConnectivity() — Backoff exponencial 10s → 5min
    ├─► connectWebSocket()    — Canal WSS persistente con el portal
    │
    ├── LOOP SCAN ─────────────────────────────────────────────┐
    │   Descubre y lee impresoras (SNMP/EWS/PJL/IPP)            │
    │   Frecuencia adaptativa según horario laboral del sitio   │
    │
    ├── LOOP SYNC ─────────────────────────────────────────────┐
    │   Cada 30s: sube lotes de lecturas pendientes al portal   │
    │   Purga registros ya sincronizados o vencidos (7 días)    │
    │
    └── CANAL WEBSOCKET ───────────────────────────────────────┘
        Recibe comandos en tiempo real del portal (forzar scan,
        actualizar configuración, resetear impresora, etc.)

Frecuencia Adaptativa por Horario Laboral

El agente ajusta la cadencia de escaneo según el horario laboral configurable del sitio (días, franja horaria y zona IANA definidos desde el portal), reduciendo tráfico de red fuera de horario sin dejar de monitorear:

Dentro del horario laboral

Descubrimiento de red cada 10 minutos, contadores cada 20 minutos, insumos cada 60 minutos y verificación de alertas cada 3 minutos.

Fuera del horario laboral

Descubrimiento cada 60 minutos, contadores e insumos cada 4 horas, alertas cada 15 minutos.

Canal en Tiempo Real (Comandos Remotos)

El WebSocket seguro (WSS, puerto 443) es bidireccional: además de que el agente pueda notificar eventos, el portal puede empujar comandos hacia el agente sin que este tenga que consultar (polling) constantemente — por ejemplo, forzar un escaneo inmediato, pedir un reset remoto de una impresora o actualizar la configuración de rangos IP. El canal se reconecta automáticamente ante cortes de red.

3–4. Red y Seguridad

3. Red Zero-Inbound: Sin Puertos Abiertos

Para integrarse sin fricción en redes corporativas reguladas (banca, salud, sector público), el agente opera bajo un paradigma Zero-Inbound:

  • Sin sockets de entrada: El agente nunca escucha conexiones desde afuera. No hay superficie de ataque perimetral que exponer.
  • Todo el tráfico es saliente: HTTPS y WSS estándar, siempre sobre el puerto TCP 443, indistinguible en el firewall del tráfico normal de navegación cifrada.
  • Soporte de proxy corporativo: Si la red exige salida vía proxy, el agente lo usa automáticamente mediante HTTP CONNECT tunneling, tanto para la sincronización como para el WebSocket.
  • Backoff exponencial ante cortes: Los reintentos de conexión escalan de 10 segundos a un techo de 5 minutos, evitando saturar firewalls o el propio portal cuando cae la WAN.

4. Identidad Criptográfica por Hardware (HWID Binding)

La configuración local del agente (URL del portal, credenciales, rangos IP) se guarda cifrada en config.enc, atada de forma irreversible al equipo físico donde se instaló:

Flujo de Derivación Criptográfica
[MachineGuid] + [Serial BIOS] ──► SHA-256 ──► Hardware ID
                                                    │
                                                    ▼
                                        PBKDF2 (210.000 iteraciones)
                                                    │
                                                    ▼
[Config JSON] ──► AES-256-GCM ◄──────────── Clave derivada
                       │
                       ▼
                config.enc en disco
Por qué importa: Si alguien copia config.enc a otra máquina para robar credenciales, el Hardware ID calculado en esa máquina es distinto y el descifrado falla de inmediato (HWID_MISMATCH). El archivo es inútil fuera del equipo original.

5. Descubrimiento

5. Descubrimiento y Captura de Impresoras

Ninguna impresora habla un único protocolo de forma confiable, y dos modelos del mismo fabricante pueden exponer los contadores en lugares distintos. El motor de captura resuelve esto identificando primero qué dispositivo es, y recién después decidiendo cómo leerlo — con un archivo declarativo por modelo y familias de protocolo compartidas, la misma disciplina que usan las plataformas MPS comerciales.

Flujo de Captura por Dispositivo
  1. Sondeo de puertos TCP (9100, 631, 80, 443)
       │   500 ms para 9100/631 · 2.000 ms para 80/443 (firmware EWS lento)
       │
       ├─ ¿9100 o 631 abiertos? ──► impresora confirmada
       │
       └─ ¿solo 80/443 abiertos? ──► podría ser router/NAS/PC
               └─ se exige validación SNMP como impresora antes de
                  intentar HTTP, evitando falsos positivos de
                  escaneo web sobre infraestructura de red

  2. IDENTIFICAR    SNMP (sysObjectID, hrDeviceDescr) → sondas EWS de
                    las familias → PJL → IPP

  3. RESOLVER       perfil del modelo exacto, si existe
                    → familia de protocolo por puntaje
                    → Printer-MIB genérica como red de seguridad

  4. RECOLECTAR     la familia resuelta lee los ámbitos pedidos:
                    identidad · contadores · insumos · alertas · bandejas

  5. COMPLETAR      los huecos que hayan quedado se rellenan con
                    Printer-MIB → PJL (total) → IPP (identidad)

Ámbitos de Captura Independientes

La lectura no es monolítica: el motor recibe qué ámbitos (scopes) necesita en cada ciclo — descubrimiento, contadores, insumos o alertas — y sólo interroga lo necesario. Por eso el agente puede leer alertas cada 3 minutos sin volver a hacer un descubrimiento completo de red cada vez, manteniendo el tráfico en la intranet del cliente al mínimo.

Cobertura Multi-Fabricante

El motor combina perfiles de modelo específicos (HP, Lexmark, Samsung) con familias de protocolo compartidas para el resto del parque, y usa la Printer-MIB estándar como respaldo universal para cualquier equipo sin perfil propio. Todo el parseo se hace con expresiones regulares y lectores planos sobre HTML/XML/JSON — sin motor de navegador embebido, lo que mantiene el consumo de memoria del agente en el orden de decenas de MB.

6. Persistencia y Resiliencia

6. Persistencia Local y Tolerancia a Fallas de Red

El agente guarda todo lo que lee en una base de datos SQLite local (modo Write-Ahead Logging) antes de intentar enviarlo a la nube. Esto lo hace funcionalmente independiente de la conectividad WAN:

Tabla Propósito
readings_queueCola de lecturas pendientes de sincronizar (contadores, insumos, seriales, método de lectura).
known_devicesCaché de dispositivos ya identificados por IP, incluido el método de lectura preferido (hint).
Backpressure

Si la cola supera 10.000 registros pendientes (por ejemplo, WAN caída por varios días), el agente pausa el escaneo hasta liberar espacio, protegiendo el disco local.

Retención y purga

Cada ciclo de sincronización elimina registros ya enviados o con más de 7 días de antigüedad, manteniendo el archivo local estable.

Garantía práctica: Con espacio en disco disponible, el agente puede operar hasta 7 días sin conexión a internet sin perder ninguna lectura. Al reconectar, drena la cola en orden cronológico y la plataforma recibe la serie temporal completa, sin huecos ni duplicados (el envío por lotes es idempotente).

7. Autenticación y Actualizaciones

7. Autenticación y Actualizaciones Firmadas

A. Autenticación Rotativa de Doble Token

El agente no guarda una contraseña fija de por vida. Usa un esquema de tokens de corta duración que se renuevan solos:

  1. Activación: una clave efímera, válida 24 horas, se usa una única vez al instalar.
  2. Refresh Token: el portal emite un token de 64 bytes que el agente guarda cifrado en config.enc.
  3. Access Token (JWT): token de corta duración usado en cada request normal.
  4. Rotación automática: si el portal responde 401, el agente usa el refresh token para obtener un par nuevo de tokens sin intervención humana.

B. Actualizaciones de Firmware Firmadas (Ed25519)

El actualizador automático del agente verifica dos firmas antes de instalar cualquier versión nueva, mitigando ataques de cadena de suministro:

  • Integridad: hash SHA-256 del paquete descargado, verificado contra el declarado por la API.
  • Autenticidad: firma digital Ed25519 verificada contra una clave pública fija embebida en el binario del agente. Si la firma no valida, el archivo se borra de inmediato y se genera una alerta crítica — nunca se ejecuta código sin firma verificada.
Para el equipo de sistemas del cliente: el agente se actualiza solo, sin requerir acceso remoto al equipo ni ventanas de mantenimiento coordinadas — la verificación criptográfica reemplaza la necesidad de supervisión manual de cada actualización.

Para el detalle de implementación (constantes, funciones, formatos de parseo por fabricante), ver STC_Agente_Funcionamiento_Interno y STC_Guia_Arquitectura_Tecnica en esta misma carpeta.
