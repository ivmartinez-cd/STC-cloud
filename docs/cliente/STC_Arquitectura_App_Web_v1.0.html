1. Visión General

1. Dos Aplicaciones, un Mismo Host: Portal y API

"La app web" de STC Cloud son en realidad dos aplicaciones independientes que se despliegan juntas: un portal (interfaz que usan los clientes y administradores desde el navegador) y una API (el servidor Fastify que recibe tanto al portal como a los agentes instalados en cada sitio). Todo corre self-hosted en un único host mediante Docker Compose, sin depender de un proveedor cloud propietario.

El backend confía en nginx como proxy inmediato (trustProxy: true) para resolver la IP real del cliente vía X-Forwarded-For. Portal y API son contenedores separados con su propio Dockerfile; nginx enruta /api/ y /ws hacia la API y todo lo demás hacia el portal estático.

Nota de escala actual: el despliegue asume explícitamente una sola réplica del contenedor api — varios procesos en segundo plano usan temporizadores simples (setInterval) en vez de colas distribuidas porque no hay más de una instancia corriendo a la vez. Escalar horizontalmente la API requeriría migrar esos procesos a colas (algunos, como el envío de notificaciones, ya usan BullMQ y sí soportan múltiples réplicas).

2. Backend: Arranque y Módulos

2. Arranque y Organización Modular

El servidor Fastify sigue una secuencia de arranque estricta y verificable (server.ts): valida variables de entorno críticas, corre las migraciones de base de datos pendientes, crea un usuario administrador por defecto si la base está vacía, y solo entonces registra rutas y abre el puerto.

Secuencia de Arranque
  start()
    ├─► JWT_SECRET ausente?          ──► aborta el proceso (falla rápido, no arranca a medias)
    ├─► db.migrate.latest()          ──► aplica migraciones pendientes de Postgres
    ├─► bootstrapDefaultAdmin()      ──► crea admin inicial si la tabla users está vacía
    ├─► registro de plugins base     ──► CORS, métricas, manejo de errores, rate limit
    ├─► registerAllRoutes()          ──► ~20 módulos de negocio
    ├─► WebSocket (/ws)              ──► agentes DCA + portal
    └─► fastify.listen()             ──► + graceful shutdown

Arquitectura Hexagonal por Módulo

El backend está organizado en cerca de 20 módulos de negocio independientes (src/modules/): auth, agents, devices, alerts, incidents, clients, reports, scheduled-reports, supplies, supply-requests, remote-actions, two-factor, public-api, audit, observability, dashboard, inventory, device-costs, email-log, system-settings, message-templates, activity-views, metrics y feedback. Cada módulo separa sus responsabilidades en cuatro capas:

Capa Contenido
domain/Entidades, reglas de negocio puras, interfaces de repositorio y errores del dominio — sin dependencias externas.
application/Casos de uso (orquestan el dominio) y puertos hacia infraestructura.
infrastructure/Adaptadores concretos: acceso a Postgres vía Knex, colas, servicios externos.
presentation/Controllers y definición de rutas Fastify, únicamente lo que el módulo expone hacia afuera.

El módulo auth es el más grande y ejemplifica el patrón: separa el caso de uso de login, la gestión de usuarios, y controllers dedicados por responsabilidad (autenticación de agentes, sesión de portal, gestión de usuarios, estadísticas de login, versión de agente).

3. Auth, Roles y Multi-Cliente

3. Autenticación, Roles y Aislamiento Multi-Cliente

La API distingue tres tipos de identidad que se conectan a ella, cada uno con su propio esquema de autenticación:

Agentes (DCA)

JWT propio del agente instalado en el cliente. Se valida contra una lista de revocación en Redis para poder desactivar un agente sin esperar que expire su token.

Usuarios del portal

JWT en cookie httpOnly (stc_session), nunca expuesto a JavaScript. Exige 2FA activo si la cuenta lo tiene forzado, en cualquier ruta salvo login/2FA.

Integraciones ERP

Header X-Api-Key de alta entropía, sin JWT. Sólo se guarda el hash SHA-256 de la clave en base de datos, nunca el valor en claro.

Control de Acceso por Rol (RBAC)

Existen tres roles: admin y operator (sin restricciones de rutas) y client_viewer, limitado a una allowlist explícita de rutas de lectura. El diseño es deliberadamente deny-by-default en dos ejes: un rol no reconocido no accede a nada, y una ruta no listada tampoco. Al arrancar, el servidor verifica que cada ruta de la allowlist exista realmente registrada — un error de tipeo hace fallar el arranque en vez de denegar en silencio.

Detalle deliberado de seguridad: la allowlist de client_viewer excluye a propósito los endpoints que exponen la comunidad SNMP de un agente o sus logs internos, aunque en general pueda ver el resto de los datos de sus propios dispositivos.

Aislamiento entre Clientes (Multi-Tenancy)

Cada cliente de STC Cloud es una fila en la tabla clients. La columna client_id se propaga a usuarios, agentes, dispositivos y al registro de auditoría, y el aislamiento se aplica en dos capas redundantes: la validación de "pertenencia" de un recurso (:id) se hace de forma centralizada en el middleware de autenticación —no depende de que cada endpoint nuevo se acuerde de filtrar por cliente— y además cada consulta a base de datos scopea explícitamente por client_id.

4. Base de Datos y Jobs

4. Base de Datos y Procesos en Segundo Plano

La plataforma usa PostgreSQL con la extensión TimescaleDB, pensada para series temporales de alto volumen (lecturas de contadores de miles de impresoras a lo largo del tiempo), administrada mediante Knex (72 migraciones versionadas al momento de este documento).

Procesos en Segundo Plano

Todos los procesos corren dentro del mismo contenedor api, combinando dos mecanismos según la necesidad: colas BullMQ sobre Redis (para trabajo que debe sobrevivir un reinicio y eventualmente correr en varias réplicas) y temporizadores simples (para tareas periódicas de instancia única):

Proceso Mecanismo Función

incidentWorkerTimerAgrupa alertas relacionadas en incidentes.
heartbeatMonitorTimerDetecta agentes caídos y dispara alertas de conectividad.
notificationWorkerBullMQEntrega emails y webhooks de alertas, incidentes y pedidos de insumos.
publicWebhookWorkerBullMQDispara webhooks salientes a los ERP de cada cliente.
remoteActionWorkerTimerDespacha y reconcilia acciones remotas hacia los agentes.
reportDeliveryWorkerBullMQGenera y envía reportes (CSV/XLSX/PDF) por email, webhook o SFTP.

5. Tiempo Real e Integraciones

5. Tiempo Real (WebSocket) e Integraciones Externas

Un único endpoint /ws atiende tanto a los agentes instalados en los clientes como a las sesiones del portal abiertas en el navegador, distinguiendo el tipo de conexión al autenticar.

  • Tickets de un solo uso para el portal: en vez de pasar el token de sesión completo por la URL del WebSocket (quedaría en logs de proxies), el portal primero pide un ticket de corta duración (60 segundos) y lo usa una única vez para abrir el canal.
  • Escalamiento horizontal vía Redis pub/sub: si en el futuro hay más de una réplica de la API, los sockets de distintos usuarios del portal quedan repartidos entre procesos. Un canal Redis dedicado retransmite los mensajes entre réplicas para que lleguen al socket correcto sin importar en qué proceso esté conectado.
  • Comandos remotos "síncronos" sobre un transporte asíncrono: cuando un administrador pide una acción sobre una impresora concreta (por ejemplo, leer su configuración EWS en vivo), el pedido HTTP del portal queda esperando hasta que el agente responde por WebSocket, dando la sensación de una operación síncrona sin serlo realmente — y sin mezclar esa respuesta con la de otros administradores conectados al mismo tiempo.

API Pública para Integraciones ERP

El módulo public-api expone lecturas de dispositivos y configuración de webhooks salientes a sistemas externos (ERPs de los clientes), autenticado por API Key en vez de sesión de usuario. Las lecturas destinadas a un ERP se procesan en una cola separada de la sincronización normal de los agentes, para que una entrega lenta hacia un sistema externo no retrase el ingreso de datos de los propios agentes.

6. Frontend: Stack y Navegación

6. Stack, Organización por Features y Navegación

El portal es una SPA en React 19 + TypeScript, construida con Vite y estilizada con Tailwind CSS 4. No usa una librería de manejo de estado global (Redux/Zustand) ni una librería de data-fetching (React Query/SWR): el estado global se resuelve con dos Contexts de React (sesión y notificaciones tipo toast) y cada pantalla trae sus propios datos con hooks propios.

Organización por Dominio (Feature-Based)

El código del portal se organiza por funcionalidad de negocio, no por tipo de archivo. Cada carpeta bajo src/features/ es autocontenida (páginas, componentes y hooks propios):

Operación

devices, pending-devices, monitors (agentes + consola remota), incidents, alerts

Gestión

clients, supplies, supply-requests, settings

Reporting

reports, scheduled-reports, activity, email-log

Una regla de arquitectura vigilada automáticamente en CI impide que una feature importe código de otra feature directamente, y que el código compartido (shared/, store/, app/) dependa de una feature — la dependencia va siempre en un solo sentido.

Navegación y Control de Acceso en la Interfaz

Todas las páginas se cargan de forma perezosa (lazy()) para dividir el bundle por ruta. Fuera del login, todo el árbol de rutas exige sesión activa; además, las rutas exclusivas de administración (gestión de agentes, reportes programados, log de emails, acciones remotas, auditoría de actividad, dispositivos pendientes) están protegidas también por componente de rol en el propio router — así un usuario client_viewer no puede acceder tecleando la URL directamente, aunque esa opción no aparezca en su menú.

7. Sesión y Datos en Vivo

7. Sesión Sin JWT Visible: Cookies, CSRF y Datos en Vivo

El portal nunca maneja el token de sesión directamente en JavaScript. La autenticación viaja en una cookie httpOnly, invisible para el propio código del frontend y por lo tanto inalcanzable para un ataque de scripting (XSS) que intente robarla.

  • Protección CSRF de doble cookie: junto a la cookie de sesión, el servidor entrega una segunda cookie legible por JavaScript con un token anti-CSRF, que el portal reenvía como header en cada operación de escritura. Un sitio externo que intente falsificar una petición no puede leer esa cookie ni, por lo tanto, construir el header correcto.
  • Manejo centralizado de sesión vencida: un 401 (sesión inválida) redirige siempre al login; un 403 (falta de permiso de rol) no cierra la sesión, solo muestra el mensaje del backend — la distinción evita deslogueos innecesarios cuando el problema es de permisos, no de autenticación.

Datos en Vivo: Polling, no un Socket Global

A diferencia de lo que podría esperarse, el portal no mantiene un canal WebSocket permanente para refrescar pantallas: cada bloque de cada pantalla actualiza sus datos por sondeo periódico (cada 60 segundos), de forma independiente entre sí — si un bloque falla, no afecta al resto de la pantalla. La única excepción real a tiempo real es la consola remota de un agente específico, que sí abre un WebSocket dedicado (con el ticket de un solo uso descripto en la sección 5) mientras esa vista está abierta.

Por qué importa esta elección: el polling desacoplado hace que una pantalla compleja (por ejemplo, un dashboard con múltiples widgets) no dependa de un único canal en tiempo real que, si se cae, dejaría toda la pantalla congelada. Cada widget se recupera solo en su siguiente ciclo de sondeo.

8. Calidad y Despliegue

8. Controles Automáticos de Arquitectura (CI)

Varias de las reglas descriptas en este documento no dependen únicamente de la disciplina del equipo: están verificadas por scripts que corren en cada cambio y bloquean el pipeline si se violan, con un esquema de ratchet — el código ya existente que no cumple queda congelado en una lista base, pero nada nuevo puede empeorar esa lista.

Control Qué garantiza
check-routes.mjsCada ruta de la API declara explícitamente su autenticación, salvo que esté en una lista pública explícita — ninguna ruta queda "olvidada" sin proteger. Además regenera el catálogo de permisos de la documentación interna.
check-guards.mjsFronteras de dependencia entre capas (dominio/aplicación/infraestructura en el backend, entre features en el portal), prohíbe logs de depuración fuera de tests y manejo de errores silencioso sin justificar.
check-sizes.mjsLímite de tamaño por archivo y por función tanto en el backend como en el portal, para evitar que un módulo crezca sin control con el tiempo.
check-icons.jsEvita que el portal referencie íconos que no existen en la librería de íconos.

El despliegue completo (nginx, portal, API, base de datos, Redis, renovación de certificados TLS y backups periódicos) se orquesta con un único docker-compose.prod.yml, de modo que el mismo entorno se reproduce de forma idéntica en pruebas y en el servidor definitivo.

Para la arquitectura del componente instalado en la red del cliente, ver STC_Arquitectura_Agente en esta misma carpeta.
