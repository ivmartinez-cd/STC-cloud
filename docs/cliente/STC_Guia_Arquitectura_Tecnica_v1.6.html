2. Arquitectura de Red: Zero-Inbound

Para integrarse sin fricciones en entornos corporativos altamente regulados (banca, salud, sector público), el agente opera bajo un paradigma de Zero-Inbound (Entrada Cero):

  • Sin Puertos de Entrada Abiertos: El agente nunca escucha peticiones desde el exterior. No se expone ningún socket entrante en la red del cliente, anulando la superficie de ataque perimetral.
  • Conexiones de Salida Seguras (Outbound-Only): Todo el flujo hacia el portal en la nube se realiza a través de peticiones HTTP/S estándar y canales WebSocket Seguros (WSS) bidireccionales en el puerto estándar TCP 443.
  • Tolerancia y Backoff Exponencial: Si se pierde el canal WAN, el agente utiliza un algoritmo progresivo (`waitForConnectivity`) que espacia los intentos de conexión desde 10 segundos hasta un techo de 5 minutos, previniendo inundaciones en los firewalls locales y servidores externos.

3. Hardware ID Binding

3. Derivación de Claves por Hardware (HWID Binding)

Para impedir el robo de credenciales y asegurar que una configuración local (`config.enc`) no pueda ser trasladada o clonada en otra máquina física, el agente implementa un cifrado de vinculación física estricto (Hardware Binding):

Flujo de Derivación Criptográfica
[MachineGuid] + [BIOS Serial] ──► [String Crudo] ──► [SHA-256 Hash] ──► [Hardware ID (32 chars hex)]
                                                                                  │
                                                                                  ▼
                                                                       [PBKDF2 (100k iter, sha256)]
                                                                                  │
                                                                                  ▼
[JSON de Config] ──► [Cifrado Simétrico AES-256-GCM] ◄────────────────────── [Derived Key]
                                 │
                                 ▼
                     [config.enc en Disco]

Especificaciones Técnicas del Proceso

  1. Extracción de Identificadores (Windows):
    • Consulta el parámetro único de instalación de Windows mediante el registro del sistema:
      Registry::HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Cryptography\MachineGuid
    • Extrae el número de serie de hardware físico de la placa base/BIOS por consulta WMI/CIM nativa:
      Win32_BIOS.SerialNumber
  2. Derivación del HWID base: Combina ambos strings en el formato `${guid}-${bios}` y ejecuta un hashing unidireccional SHA-256. Los primeros 32 caracteres hexadecimales resultantes componen el identificador único de hardware.
  3. Función de Derivación de Claves (KDF): Para blindar la clave simétrica ante ataques de fuerza bruta en memoria, aplica **PBKDF2** (Password-Based Key Derivation Function 2) alimentado por el HWID base, una sal criptográfica de 16 bytes generada en el disco en caliente, y **100,000 iteraciones** del motor `sha256`. Esto produce la clave final de cifrado de 32 bytes (256 bits).
  4. Cifrado Simétrico Integrado (AES-256-GCM): Genera un vector de inicialización (IV) criptográfico de 12 bytes aleatorios. Cifra los datos sensibles y calcula un tag de autenticación de 16 bytes. Escribe el buffer binario estructurado en `config.enc`.
  5. Prevención contra Manipulación y Clonado: Si un atacante copia el archivo `config.enc` a otra máquina, el agente intentará leer la BIOS y el Guid local de esa nueva máquina para descifrar el tag de autenticación. Esto causará un fallo criptográfico inmediato (`BAD_DECRYPT` o `Invalid authentication tag`), disparando la excepción preventiva `HWID_MISMATCH` y bloqueando la ejecución.

4. Escaneo e Inmunidad IDS

4. Algoritmo y Cascada de Descubrimiento de Impresoras

El subsistema de escaneo (`scanner.ts`) está diseñado de manera defensiva. Su prioridad es **no activar alertas de intrusión en la intranet** (evitar falsos positivos en firewalls perimetrales, WAF o sistemas SIEM) y optimizar la precisión de datos de contadores.

A. Precalificación de Puertos por Socket TCP Crudo

Antes de enviar tramas HTTP o comandos complejos, el agente ejecuta una sonda paralela rápida en los puertos TCP `9100`, `631`, `80` y `443` con un timeout estricto de **500 ms** (`REACH_TIMEOUT = 500`). Concurrencia regulada mediante semáforo a un máximo de 20 IPs simultáneas.

B. La Bifurcación de Aislamiento de Seguridad (`hasPrinterPort`)

El agente implementa una lógica booleana determinante para decidir qué protocolos está autorizado a interrogar en cada dirección IP: 

const hasPrinterPort = openPorts.has(PORT_JETDIRECT) || openPorts.has(PORT_IPP);
  • Caso `hasPrinterPort === false` (Aislamiento de Seguridad): Si los puertos exclusivos de impresión TCP `9100` (JetDirect) y TCP `631` (IPP) están **cerrados**, el agente asume inmediatamente que el host es un dispositivo de infraestructura general (servidor web, switch, Active Directory, NAS, router, PC de usuario).
    Acción: El agente **cancela y omite cualquier petición HTTP/S a los puertos 80/443**. Pasa de inmediato y de forma exclusiva a una consulta SNMP de lectura básica de MIBs estándar. Esto elimina falsas alarmas de escaneo web perimetral.
  • Caso `hasPrinterPort === true` (Dispositivo Confirmado): Si el puerto `9100` o el `631` está abierto, se confirma la existencia física de una impresora en red. El agente queda habilitado para realizar HTTP/S Scraping y el resto de la cascada con seguridad.

C. Flujo Secuencial de Cascada y Fallback en Caliente

Para impresoras confirmadas, el agente interroga secuencialmente hasta hallar contadores válidos (`total_pages !== null`), en la siguiente jerarquía:

  1. Nivel 1: EWS (HTTP/S Scraping - Puertos 80/443): Scraping HTML/XML de administración. Obtiene datos literales y directos tal cual los calcula la impresora. Si obtiene contadores, detiene la cascada.
  2. Nivel 2: SNMP v2c (UDP Puerto 161): Consulta de MIBs RFC 3805/2790 con timeout de **3000 ms** (`TIMEOUT_MS = 3000`) y **1 reintento** (`RETRIES = 1`). Valida la OID `hrDeviceType` para confirmar tipo impresora física; si no coincide, aborta la lectura. Si obtiene contadores, detiene la cascada.
  3. Nivel 3: PJL (TCP Puerto 9100): Conexión TCP y comandos directos de conteo (por ejemplo, `@PJL INFO PAGECOUNT` y `@PJL INFO ID`). Si obtiene contadores, detiene la cascada.
  4. Nivel 4: IPP (TCP Puerto 631): Envío de tramas de atributos estandarizados (`Get-Printer-Attributes`).
  5. Coalescencia Nullish (`ews ?? snmpResult ?? pjl ?? null`): Si ningún método entregó contadores consolidados, fusiona los datos parciales para rescatar la identidad básica (número de serie, marca, modelo).

D. Caché Persistente: Ruta Rápida (Fast Path)

Una vez que se identifica el método exitoso, este se persiste en la base SQLite bajo la columna `poll_method`. En los ciclos siguientes, el agente ejecuta el protocolo cacheado de forma **directa y directa**, saltándose la verificación de puertos y la cascada secuencial. Si el dispositivo falla, la caché se invalida a `'unknown'` y se vuelve a lanzar el descubrimiento dinámico.

5. Motor de Extracción EWS

5. Motor de Extracción Quirúrgica via EWS

El motor de telemetría por EWS (Embedded Web Server) implementado en ews.ts representa la capa de mayor precisión del agente. Permite extraer contadores y estados de consumibles directamente de las páginas administrativas nativas del hardware, operando de manera aislada y sin consumo excesivo de red.

A. Capa de Transporte y Control de Red (`fetchHttp`)

Diseñado sobre los módulos nativos http y https de Node.js, garantizando un binario libre de librerías externas de red (evita dependencias como Axios).

  • Límite de Espera Estricto: Se fija en **4000 ms** (EWS_TIMEOUT = 4000). Si la CPU de la placa de red de la impresora está saturada, se destruye el socket de inmediato (req.destroy()) liberando el Event Loop del agente.
  • Bypass TLS para Intranet: Configura rejectUnauthorized: false. Es mandatorio para saltarse advertencias de certificados auto-firmados o expirados habituales en impresoras corporativas locales.
  • Manejador de Redirecciones (Anti-Loop): Sigue estados 301, 302, 307 y 308 recalculando esquemas y rutas dinámicas. Cuenta con un límite de **3 saltos** (redirectDepth = 3) para evitar bucles infinitos causados por portales cautivos.

B. Matriz Quirúrgica de 13 Endpoints

El agente no realiza un rastreo (crawl) genérico. Interroga de forma directa una matriz ordenada de URLs específicas:

Fabricante / Tipo Endpoint Clave del Firmware Objetivo de Telemetría
Samsung SWS /sws.application/information/countersView.sws Contadores físicos consolidados
Samsung SyncThru /sws/app/information/counters/counters.json Contadores en formato JSON nativo
Lexmark Reports /cgi-bin/dynamic/printer/config/reports/deviceinfo.html Páginas totales, serial y modelo
HP FutureSmart /DevMgmt/ProductUsageDyn.xml API XML estructurada de HP
HP Usage Page /hp/device/InternalPages/Index?id=UsagePage Contador físico (HTML responsive)

C. Acumulador Incremental y Cortocircuito (Billing Guard)

El agente procesa secuencialmente la matriz en un bucle cerrado. Inicializa un objeto acumulador dinámico (acc) y vuelca los datos extraídos de cada endpoint exitoso mediante una estrategia de fusión conservadora: solo escribe propiedades si el nuevo valor no es indefinido (por ejemplo, combina el modelo de identity.json con contadores de counters.json).

Cortocircuito de Facturación: En el instante exacto en que acc.totalPages es exitosamente poblado, el agente rompe la ejecución del bucle (break) y retorna los datos. Esto evita realizar las peticiones HTTP/S restantes a otros endpoints de la matriz, reduciendo el tráfico de red local en un 70%.

D. Parseo de Datos sin Motor Web (Headless Free)

Para anular vulnerabilidades de scripting y reducir la huella de memoria RAM a kilobytes, el agente no levanta navegadores embebidos ni procesa el DOM. Utiliza expresiones regulares deterministas y lectores XML planos:

  • Lector XML Determinista (HP): Extrae los valores de etiquetas como <TotalImpressions> mediante expresiones regulares de etiquetas limpiando signos de millares.
  • Regex Multilingüe (Español / Inglés / Coreano): Busca cadenas físicas específicas como gxi-billing-simplex-bw-total-cnt (simplex) o Cómputo de pág. (Page Count) aislando el entero continuo.
  • Suma de Facturación Simplex/Duplex: En JSONs de Samsung, extrae y suma las variables GXI_BILLING_SIMPLEX_BW_TOTAL_CNT y GXI_BILLING_DUPLEX_BW_TOTAL_CNT para evitar omisiones de impresión a doble cara.

6. Arquitectura de Almacenamiento Local (SQLite WAL)

El agente aloja la cola de telemetría e histórico de lecturas en una base de datos local SQLite administrada bajo el motor nativo better-sqlite3:

  • Write-Ahead Logging (PRAGMA journal_mode = WAL): Permite operaciones de lectura y escritura concurrentes sin bloqueos de hilos (Thread Blocking).
  • Control de Backpressure: Para evitar llenar el disco local si se interrumpe la conexión WAN de manera indefinida, el agente implementa un límite estricto de **10,000 registros en cola**. Si se supera, los escaneos de red se pausan preventivamente.
  • Autolimpieza y Retención: Cada proceso de sincronización purga automáticamente los registros sincronizados (synced = 1) y aquellos con antigüedad superior a los **7 días**, manteniendo el archivo estable en disco.

7. Autenticación Rotativa de Doble Token

Para proteger las APIs de ingesta del canal en la nube sin almacenar credenciales perennes en los equipos clientes, STC Cloud utiliza un sistema dinámico:

  1. Clave de Activación Efímera: Clave uniuso válida por 24 horas enviada durante la instalación.
  2. Refresh Token Rotativo: Al activarse, la API de la nube le asigna un token criptográfico de 64 bytes que se persiste de forma cifrada en la configuración local.
  3. Access Token JWT (Corto Plazo): Las peticiones normales usan un JSON Web Token (JWT) temporal con expiración de unas pocas horas.
  4. Rotación Activa en Caliente: Si la petición al portal devuelve un HTTP 401 Unauthorized, el agente lanza de forma asíncrona un flujo de renovación (tryRefresh) enviando el Refresh Token. La nube verifica el hash SHA-256 en la base relacional (refresh_token_hash), destruye el refresh token anterior, emite una nueva pareja de tokens y el agente actualiza su archivo config.enc.

8. Protocolo de Firma de Actualización de Firmware (Ed25519)

El actualizador automático implementa un flujo criptográfico asimétrico de dos firmas para mitigar vulnerabilidades críticas de cadena de suministro (Supply Chain Attacks):

  • Integridad por Hash SHA-256: Descarga el archivo de firmware comprimido y computa su hash SHA-256 para validarlo frente a la firma declarada por la API HTTPS.
  • Firma Digital de Clave Pública Fija (Ed25519): El agente descarga adicionalmente un archivo de firma digital .sig. Utilizando el motor criptográfico nativo de Node.js, verifica la firma digital del binario contra la clave pública maestra inmutable e inyectada en su binario (UPDATE_PUBLIC_KEY_HEX). Si la firma falla, se elimina inmediatamente el archivo descargado de forma preventiva y se genera una alerta crítica.
