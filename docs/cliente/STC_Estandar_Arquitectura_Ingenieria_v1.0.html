Contexto y Estándar

1. Por qué esto le importa a su área

Cuando su organización incorpora un sistema, hereda el riesgo de cómo fue construido. Un software sin estándar de arquitectura funciona igual de bien el primer día y se degrada de forma predecible: cada cambio tarda más, cada corrección introduce dos errores nuevos, y llega un punto en que el proveedor recomienda "rehacerlo" porque nadie entiende el código que escribió el año pasado.

Un estándar de arquitectura verificado le da tres garantías concretas:

Continuidad

El código no depende de que una persona específica lo recuerde. La estructura es explícita y uniforme en los 24 módulos del sistema: un desarrollador nuevo ubica dónde vive cada cosa sin arqueología.

Cambios acotados

Las dependencias entre partes están restringidas por regla, no por costumbre. Un cambio en facturación no puede romper alertas, porque el código que lo intentara no pasa la verificación automática.

Auditabilidad

Las afirmaciones de este documento no son declarativas: cada una corresponde a un script que corre en el pipeline y falla si deja de ser cierta. Usted puede pedir la salida de esos scripts.

Reversibilidad

Las 75 migraciones de base de datos tienen su operación inversa (down) escrita y versionada. Un despliegue que salga mal se revierte, no se parchea a mano sobre la base productiva.

2. El estándar que seguimos

El equipo trabaja contra un documento normativo interno, la Guía de Arquitectura de Proyectos, que fija en 12 capítulos las reglas de estructura, nomenclatura, tamaños máximos, manejo de errores, testing, seguridad, control de versiones y rendimiento. No es un manifiesto genérico: es la norma contra la cual se revisa cada cambio y contra la cual corren las verificaciones automáticas descritas en §5.

Sus fundamentos son los estándares de la industria, no invenciones propias:

FundamentoQué impone en la práctica
SOLID Cada unidad de código tiene una sola responsabilidad y depende de abstracciones, no de implementaciones concretas. En la práctica: se puede reemplazar la base de datos, el proveedor de correo o el almacenamiento sin tocar la lógica de negocio.
Arquitectura hexagonal
(puertos y adaptadores)		 La lógica de negocio no conoce a la tecnología que la rodea. La base de datos, la API HTTP y los servicios externos son piezas intercambiables enchufadas por fuera.
Clean Code Límites duros de tamaño (funciones, archivos, parámetros, anidamiento), nombres que expresan intención y prohibición explícita de patrones que degradan el código (números mágicos, objetos que hacen de todo, errores silenciados).
Monolito modular Un solo despliegue —simple de operar y de respaldar— pero internamente dividido en 24 módulos de negocio con fronteras verificadas. Se obtiene el aislamiento de microservicios sin su costo operativo.
Decisiones registradas. Las decisiones de arquitectura relevantes están documentadas como Architecture Decision Records (ADR): qué se decidió, en qué contexto y qué consecuencias se aceptaron. Hoy existen cuatro (adopción del estándar, los dos mecanismos de control de deuda descritos en §7, y el modelo de autorización de §8). Un ADR no se reescribe: si una decisión se revierte, se escribe uno nuevo que la supera. Eso deja la trazabilidad del por qué, que es lo que normalmente se pierde y lo que un auditor necesita.

Organización del Código

3. Organización del código: módulos y capas

El backend se organiza primero por módulo de negocio y dentro de cada módulo por capa técnica. Cada uno de los 24 módulos —dispositivos, alertas, insumos, reportes, incidentes, auditoría, etc.— contiene sus cuatro capas completas, de modo que una funcionalidad vive en un solo lugar del árbol de directorios.

Estructura del backend
cloud/src/
├── shared/                    Transversal: errores base, conexión a DB, tipos comunes
└── modules/
    ├── devices/               ─┐
    │   ├── domain/             │  Reglas de negocio puras. No conoce base de datos,
    │   │   ├── entities/       │  ni HTTP, ni librerías externas.
    │   │   ├── repositories/   │  (interfaces = contratos que el módulo exige)
    │   │   └── services/       │
    │   ├── application/        │  Casos de uso: orquestan el dominio. Un archivo por caso.
    │   │   ├── use-cases/      │
    │   │   ├── ports/          │  (contratos hacia afuera: correo, SNMP, archivos…)
    │   │   └── dtos/           │
    │   ├── infrastructure/     │  Implementaciones concretas: Knex/PostgreSQL, adaptadores
    │   │   ├── database/       │  a servicios externos. Aquí vive la tecnología.
    │   │   └── adapters/       │
    │   └── presentation/       │  Controladores HTTP, validadores, serialización.
    ├── alerts/                 │
    ├── supplies/              ─┘  … y así los 24 módulos, todos con la misma forma.
    └── …

La regla de dependencias

Las dependencias apuntan siempre hacia adentro. El dominio no depende de nadie; la infraestructura implementa lo que el dominio pide. Esta es la regla que evita que el sistema se convierta en una madeja:

Dirección permitida de las dependencias
   Presentation  ──▶  Application  ──▶  Domain  ◀──  Infrastructure
   (HTTP, roles)      (casos de uso)     (reglas)      (PostgreSQL, SNMP, correo)

   ✔ Infrastructure implementa las interfaces que declara Domain
   ✘ Domain NUNCA importa Infrastructure, Application ni Presentation
   ✘ Un módulo NUNCA importa las tripas de otro módulo — sólo su fachada pública

La última línea es la que sostiene el aislamiento entre dominios de negocio: el módulo de reportes puede pedirle datos al de dispositivos a través de su fachada, pero no puede alcanzar sus entidades internas ni sus tablas. Cuando mañana haya que cambiar cómo se almacenan los dispositivos, el módulo de reportes no se entera.

El portal web

El frontend sigue el mismo criterio adaptado a React: se organiza por feature (dashboard, clientes, dispositivos, alertas, reportes…), cada una con sus componentes, hooks y llamadas a la API. Una feature no importa a otra: lo compartido vive en un espacio común explícito. La regla se verifica automáticamente, igual que en el backend.

Reglas y Métricas

4. Reglas concretas y cómo se miden

Un estándar sólo sirve si sus reglas son medibles. Estas son las que impone la guía, con el criterio exacto con que se evalúan y si la verificación es automática o requiere revisión humana.

Regla Límite / criterio Verificación Qué previene
Tamaño de función 20 líneas Automática Funciones que hacen varias cosas y no se pueden probar por separado.
Tamaño de archivo 300 líneas Automática Archivos "cajón de sastre" donde termina todo lo que no tiene lugar claro.
Dirección de dependencias Sólo hacia el dominio Automática Lógica de negocio acoplada a la base de datos; imposible de cambiar o probar.
Fronteras entre módulos Sólo por fachada pública Automática Que un cambio en un dominio rompa otro sin aviso.
Fronteras entre features del portal Sin imports cruzados Automática Efectos colaterales entre pantallas que no tienen relación funcional.
Errores silenciados Prohibido catch vacío Automática Fallas que desaparecen sin dejar rastro y aparecen como "datos raros".
Trazas de depuración en producción Prohibido console.log Automática Fuga de datos a logs y ruido que tapa los errores reales.
Inyección SQL Sin SQL armado por concatenación Automática La vulnerabilidad más explotada en aplicaciones con base de datos.
Autenticación por endpoint Toda ruta declara su credencial Automática Que una ruta nueva quede expuesta sin autenticación por olvido.
Cobertura de tests por capa 90 / 85 / 70 / 60 % Automática Que la lógica crítica quede sin red de seguridad ante un cambio.
Migraciones reversibles Toda migración con down Revisión Despliegues que no se pueden revertir sin intervención manual en la base.
Formato de commits Conventional Commits Revisión Historial ilegible; imposible reconstruir qué cambió y por qué.
Aislamiento de librerías externas Detrás de interfaz propia Revisión Quedar atado a una librería que se abandona o cambia de licencia.
Sobre los componentes visuales. El límite de 20 líneas por función no se aplica al cuerpo de un componente de interfaz: un componente es una función de renderizado y medirla así produce cientos de "violaciones" sin valor. Ahí rige el límite de archivo (300 líneas) más la regla de responsabilidad única: un componente no mezcla obtención de datos, estado y maquetado; cuando lo hace, se separa. Esta excepción está escrita en el estándar, no es una interpretación de conveniencia.

Verificación Automática

5. Verificación automática en cada cambio

Esta es la diferencia entre un estándar real y uno declarativo. Las reglas de §4 no se confían a la memoria de quien programa ni a la atención de quien revisa: están implementadas como programas que analizan el código fuente y bloquean la integración del cambio si encuentran una violación nueva.

El pipeline de integración continua corre cuatro trabajos en paralelo ante cada cambio propuesto sobre la rama principal. Si cualquiera falla, el cambio no entra:

TrabajoQué ejecuta
Arquitectura Las tres guardas estáticas: límites de tamaño, reglas de dependencias entre capas/módulos/features (más errores silenciados, trazas de depuración y SQL interpolado) y declaración de autenticación en todas las rutas.
API Compilación con verificación estricta de tipos, arranque real del servidor contra PostgreSQL y Redis, suite de tests de integración y, al final, el umbral de cobertura por capa.
Portal Análisis estático, verificación de tipos, validación de iconografía y compilación de producción.
Agente Compilación, suite de tests del agente y empaquetado real —el mismo binario que distribuye el instalador, no una variante de prueba.

Las cuatro guardas, en detalle

GuardaAlcance de la verificación
Tamaños Recorre el árbol de código construyendo el árbol sintáctico de cada archivo y mide el span físico real de cada función. Excluye las migraciones de base de datos, cuyo tamaño lo determina el esquema.
Guardas de dependencias Siete reglas sobre todo el TypeScript del backend y el portal: cuatro de fronteras (capa, módulo, feature) y tres de higiene (errores silenciados, trazas de depuración, SQL interpolado).
Rutas Recorre todas las declaraciones de endpoints del backend y falla si alguna no declara qué credencial exige y tampoco figura en la lista blanca explícita de rutas públicas. Es negación por defecto en el código, no en configuración.
Cobertura Toma la cobertura real de ejecución de la suite y la agrega por capa de cada módulo, exigiendo el umbral correspondiente a cada una.
Por qué importa el orden. Las guardas no revisan el código escrito hace un año buscando culpables: bloquean lo que se agrega hoy. Esa es la única forma de que un sistema en producción mejore de manera sostenida en vez de quedar congelado esperando una refactorización total que nunca llega. El mecanismo se explica en §7.

Deuda Técnica

7. Deuda técnica declarada y controlada

Ningún sistema en producción cumple el 100 % de un estándar desde el primer día, y un proveedor que lo afirme está describiendo un sistema que no existe o un estándar que no mide nada. Lo que distingue a un proyecto sano no es la ausencia de deuda técnica, sino que la deuda esté inventariada, congelada y decreciendo.

El mecanismo: trinquete contra línea base

Cuando se adoptó el estándar sobre un sistema ya en producción, en lugar de detener el desarrollo para reescribir todo, se hizo el inventario exacto de lo que no cumplía y se lo congeló en un registro versionado. Desde entonces las guardas aplican una regla asimétrica:

  • Código nuevo: tolerancia cero. Cualquier función o archivo nuevo que exceda los límites hace fallar la verificación y el cambio no entra.
  • Código inventariado: se acepta tal como estaba, pero no puede empeorar.
  • Cuando se corrige un caso inventariado, se lo quita del registro y ya no puede volver: el listón sólo se mueve en una dirección.

El registro es un archivo versionado en el repositorio: agregar algo ahí es un cambio visible en el historial, que un revisor ve y tiene que justificar. No es una excepción silenciosa en la configuración.

Seguridad y Trazabilidad

8. Seguridad y trazabilidad de decisiones

El estándar dedica un capítulo a seguridad con reglas no negociables. Las de alcance general —validar toda entrada en el borde del sistema, nunca construir consultas por concatenación, mínimo privilegio, separar autenticación de autorización, no registrar datos sensibles— se detallan en la Guía de Auditoría de Sistemas e IT v2.1. Acá interesan las tres que son propiedades arquitectónicas verificables.

Autorización por negación por defecto, en dos ejes

El acceso a cada endpoint se resuelve cruzando dos preguntas independientes, ninguna de las cuales admite un valor por omisión permisivo:

EjePreguntaCómo se garantiza
Credencial ¿Quién llama? Usuario del portal, agente instalado o integrador con clave de API. Cada ruta declara su verificador de credencial antes de ejecutar el manejador. La guarda de rutas falla si una ruta nueva no lo declara y no está en la lista blanca pública. Verificado automáticamente.
Rol ¿Con qué permisos? Administrador, operador o usuario de cliente. El usuario acotado a un cliente sólo alcanza rutas de una lista blanca explícita; las rutas exclusivas de administrador se verifican dentro del manejador. Lista blanca verificada; la condición de rol requiere revisión humana.

El portal replica la misma condición de rol donde la interfaz necesita ocultar o deshabilitar una acción, pero el control efectivo está siempre en el servidor: ocultar un botón no es un control de seguridad.

Registro de auditoría

Toda acción administrativa —altas, bajas, cambios de estado de agentes, clientes, usuarios y configuración— queda registrada en una tabla de auditoría con actor, acción, objetivo, dirección de origen y marca temporal. El estándar exige que esa escritura pase por un único punto del código, para que ningún registro quede sin la referencia al cliente al que corresponde.

Trazabilidad de decisiones

Además del historial de cambios en formato normalizado, cada decisión de arquitectura relevante tiene su ADR con contexto, decisión y consecuencias aceptadas. Ante la pregunta de auditoría "¿por qué el sistema resuelve esto así?", la respuesta es un documento fechado y versionado, no la reconstrucción de memoria de quien lo programó.

Límites y Alcance

9. Qué no cubre la verificación automática

Un documento de arquitectura que sólo enumera fortalezas es material comercial, no material de auditoría. Estas son las limitaciones reales del esquema descrito, para que su área evalúe el riesgo con información completa.

LimitaciónAlcance real y mitigación
Las guardas verifican forma, no intención Un análisis estático confirma que una ruta declara autenticación, no que la regla de negocio que aplica sea la correcta. Eso lo cubren los tests de integración y la revisión humana, no las guardas.
La condición de rol no es verificable estáticamente Que un manejador exija rol de administrador se resuelve dentro del código y no hay forma de inferirlo automáticamente. La lista de rutas afectadas se mantiene a mano y se contrasta con tests de control de acceso.
El aislamiento de librerías externas se revisa a ojo La regla de envolver toda dependencia externa detrás de una interfaz propia se controla en revisión de código. No hay hoy una guarda que la haga fallar automáticamente.
Los umbrales de cobertura miden ejecución, no calidad Un porcentaje alto indica que el código se ejecuta durante los tests, no que las aserciones sean buenas. Es una red de seguridad contra regresiones, no una prueba de corrección.
El estándar cubre el software, no la operación Respaldos, monitoreo, retención y respuesta ante incidentes se documentan aparte y responden a otro conjunto de controles.

En síntesis

STC Cloud se construye contra un estándar de ingeniería escrito, con las reglas de mayor impacto estructural verificadas por programa en cada cambio y con la deuda remanente inventariada y en descenso controlado. Su área puede auditar cualquiera de las afirmaciones de este documento ejecutando las mismas verificaciones que ejecuta el pipeline, o solicitando su salida al equipo de desarrollo.
